# 增强功能规则

规则编号：TYPE-E。适用：主类型E已选定或顾问要求分析该类型；混合类型先明确是否拆分，不以标题替换代替类型设计。

### 5.4 E：增强

必须覆盖：标准宿主流程与目标变化；触发时点；适用组织/场景/过滤；候选增强点；输入及允许改变的输出；业务规则；宿主事务与提交限制；锁/并发；错误传播；重复触发与重入；共存和执行顺序；附加耗时；启停/撤回和标准流程回归。

区分“对象存在”“签名可读”“触发时机适用”“业务执行已经验证”。只校验而不修改数据的增强可以没有输出字段，不应虚构输出。不得擅自在宿主LUW中设计独立COMMIT；提交行为须以实际上下文为依据。

验收至少包含：触发与不触发、边界过滤、同一事务重复调用、其他增强共存、校验失败对宿主影响、宿主回滚，以及关闭增强后标准流程恢复。未取得增强上下文时保留候选与问题。

## 必须澄清的业务分歧

何时触发、哪些组织或场景生效？错误应阻止保存还是仅提示？同一事务重复触发如何处理？
能由资料、已确认规则和工具解决的先自行解决；确实未知则open+issue，不编造默认批准。专业建议写明适用条件，顾问可纠正。

## 输出合同

使用e.schema.json；contract必须完整覆盖：businessTrigger、hostProcess、enhancementObjectId、signatureAndParameters、inputFieldIds、outputFieldIds、applicabilityFilters、behaviorRuleIds、transactionAndCommit、lockingAndConcurrency、errorPropagation、repeatAndReentry、coexistenceAndSequence、performanceTarget、activationAndFallback、standardRegression。

字段含义、方向、基数、来源目标路径、精度、默认、校验、映射、单位币种在fields定义。具体处理路径放rules，每条关联requirements；数字或状态例子落tests的input/preconditions/expectedResult。对象未核验进入sapObjects并关联issues，不以工具建议替代证据。

## 数字或状态例子

只对指定工厂保存动作做数量校验，其他工厂不触发；宿主同一事务再次调用时不能重复产生外部结果；校验失败阻止保存与警告不阻止保存是不同业务决定。

## 审查及反例

每个必要主题必须有本项目明确规则或带问题的未知表达，不能只写“考虑幂等/注意事务/做好性能”。测试必须能核对对象、数值或状态；不得把例子当真实系统运行记录。未涉及的标准动作不强行加入。关键定义变更后同步修订相关测试及引用。
