# FSD 设计助手方案审视（交接）

> 2026-10-11。供新会话讨论方案方向使用，不是实施计划。本文先说现状（是什么、为什么这样设计），再列出暴露的问题和待讨论的问题；结论留给讨论。
>
> 讨论结论见 [FSD 设计助手方向决策](2026-10-11-fsd-assistant-direction-decision.md)；本文保留为决策前的现状记录。

## 1. 一句话现状

目标是让用户在对话中把报表需求变成一份可交付的 ABAP 报表 FSD，并通过 SAP 只读查询核实表、字段和配置。当前实现是**程序主导的固定流程**：LangGraph 编排 11 个节点，模型只在每个节点按严格格式“填空”。

这套方案连续开发了 4～5 天，仍不能稳定地把一个简单报表 FS 从需求跑到交付。用户的对照经验是：在 Codex 或 Claude Code 里写同样的 FS，速度快，质量也好。

| 指标                                | 数据                                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| 设计助手后端 + 文档契约代码量       | 约 8,900 行（`apps/api/src/modules/design-assistant/` + `packages/contracts/design-assistant/`） |
| 流程节点 / 运行错误码               | 11 个（N01–N11）+ 对话节点 CHAT / 43 个                                                          |
| 10-06 以来该模块的提交              | 23 次，除两次格式改造外基本是修补，多数是让模型输出适配程序约束                                  |
| 一次真实失败运行（DeepSeek-V4-Pro） | 30 分钟仍未完成：首批 4 个章节全部因格式被退回，整章重写，最后一次调用 20 分钟无响应             |

## 2. 当前方案

### 2.1 链路

```text
前端对话（ConversationTimeline.vue）
  → chat-routes.mjs / chat-service.mjs：每条用户消息生成一个“对话轮次”，挂在任务(task)下的运行(run)上
  → worker.mjs：领取运行（租约 30 s 续期），执行 LangGraph 图，结束时写聊天事件
  → graph.mjs：节点 N01–N11 + CHAT
  → model.mjs：拼提示词、调用模型；sap.mjs：调用 SAP MCP 只读工具
```

数据都在 Postgres 的 `app.fsd_v1_*` 表：task（任务状态 JSON）、run、attempt、operation（每次模型/工具调用的预留与结算）、event（节点级时间线）、commit（业务提交台账）、chat_turn / chat_event（界面看到的轮次与事件）。

### 2.2 状态控制（方案讨论的重点）

**任务层**有阶段、状态和等待原因三套状态：

- 阶段 `PHASES`：接收理解 → 业务分析 → 方案核实 → 方案确认 → FSD 编制检查 → FSD 确认 → 交付（`packages/contracts/design-assistant/protocol.mjs`）。
- 状态：ACTIVE / WAITING / PAUSED / DELIVERED / ENDED。
- 等待原因：CLARIFICATION（澄清题）、PLAN_CONFIRM（方案确认）、FSD_CONFIRM（FSD 确认）、TECHNICAL（技术失败）、BUDGET、COMPATIBILITY、CHAT_READY 等。

**流程图**（`graph.mjs`）：

| 节点            | 做什么                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------- |
| N01             | 路由：普通对话走 CHAT；“生成FSD”走 N02；重试最终稿直接到 N07                                        |
| N02             | 需求分析（AnalysisResult）→ 决定查询、提案或提问                                                    |
| N03 / N04 / N05 | 查询计划（QueryPlan）→ 执行 SAP 只读工具 → 证据评估（EvidenceAssessment），最多 3 轮                |
| N06             | 生成澄清题（ClarificationBatch），挂起等待用户答题                                                  |
| N07             | 写或修订 FSD：先写提纲，再按部分和逻辑章节并行编写（最多 4 个并发），最后写收尾部分；修订只输出变化 |
| N08             | 自审（ReviewResult），最多 2 轮修订；保存为成果版本（方案稿 PLAN 或正式稿 FSD）                     |
| N09 / N10       | 人工门：方案确认 → 回到 N07 写正式稿 → FSD 确认；未确认时中断挂起                                   |
| N11             | 交付                                                                                                |
| CHAT            | 普通对话：一次流式模型调用，**没有任何工具**，不读证据，不改文档                                    |

**用户可以做什么**（`chat-service.mjs`）：

| 用户操作         | 实际效果                                                                             |
| ---------------- | ------------------------------------------------------------------------------------ |
| 随时发普通对话   | 只聊天，不改文档；若正在等确认，对话后恢复原等待状态                                 |
| 回答澄清题       | 只能通过题目卡片回答                                                                 |
| 说“生成FSD”      | 阶段回到 1，清空所有确认，从分析重新走：查询 → 方案稿 → 方案确认 → 正式稿 → FSD 确认 |
| 出稿后提修改意见 | 写在对话里不生效，必须再说“生成FSD”，即再过两道确认、十几次模型调用                  |

**可靠性机制**（为生产级审计设计）：

- 租约与心跳、LangGraph 检查点与恢复、提交台账（防止重放时重复提交）、操作预留与结算（防止重复计费、结果未知时不重做）。
- 预算：每次运行最多 80 次模型调用、60 次工具调用、120 万 token、30 分钟有效时间；每个任务 300 次、240 次、400 万、2 小时。
- 资产固定：每次运行冻结提示词、模型、预算和图版本，版本不符时报 COMPATIBILITY。
- 证据：每条 SAP 证据要核对系统、client、版本，并有有效期。
- SAP 目标准入：manifest + 7 项能力的 PASS 证据文件（含 hash 与审批人）。

用户的担心：即使简化为“讨论 → 出稿 → 修订 → 定稿”四个状态，定稿后用户仍会做大小修改。任何显式状态机都在约束一种本质上是“反复对话改文档”的工作；Codex 或 Claude Code 没有强状态概念，对话记录和文档本身就是状态。

### 2.3 提示词

**一个系统提示词** `apps/api/src/modules/design-assistant/prompts/v1/system.md`（约 1.8 万字符，约 1.3 万 token），所有结构化调用和普通对话共用：

| 部分   | 内容                                                                                                             | 评价                                 |
| ------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 一～五 | 角色、用户、思考方法（生命周期、配置、粒度、时间口径、写操作、标准对照、反向审查）、依据纪律、提问门槛与出题方法 | 业务方法论，是真资产                 |
| 六～九 | FSD 版式与深度、阻断判定、边界、提交前自检                                                                       | 交付标准，是真资产                   |
| 十     | 输出格式：JSON（分析、查询计划等）与自定义“FSD 编写格式”（逐行可解析的 Markdown 方言）                           | 格式约束占比大，主要失败来源         |
| 十一   | 普通对话规则                                                                                                     | 对话无工具，规则管不住模型的提问质量 |

**调用类型**：AnalysisResult、QueryPlan、EvidenceAssessment、ClarificationBatch、ReviewResult 返回受 Schema 约束的 JSON；FsdOutline、FsdWrite、FsdRevise 返回 FSD 编写格式，由 `fsd-report-wire.mjs` 逐行解析成 `fsd-report/1` JSON（`fsd-report.schema.json`），再渲染成交付文档。

**每次调用的提示词** = 完整 system.md + 本次任务说明 + 事实（目标系统、证据编号）+ 冻结输入 JSON（快照、证据、分析结果）+ 提纲 + 当前文档。每个章节调用都带完整的 1.3 万 token。

**修复机制**：

- 格式不合格时由程序退回，模型重写。现在已改为每个部分最多重写一次，且只在整个部分缺失时重写。
- 合并后再按内容模型检查，不合格的部分重写一次。
- 自审最多两轮修订。

### 2.4 SAP 接入

- `.env` 的 `FSD_SAP_MODE`：10-09 为跑通流程加了 `off`；10-11 改为 `on`。
- 目标 `bestsap-s4h-100`（S/4，DEV，client 100）已登记，7 项能力证据 PASS（10-09 采集）。连通性已验证：VBAP 表结构 2 秒读回。
- 能读什么：表结构、源码、对象搜索；配置模板为空，读不了配置和数据；白名单只有 13 个对象（VBAK、VBAP、VBEP、LIKP、LIPS、VBFA、KNA1、MAKT、TVKO、VBUK、VBUP 和一个类），TVAK 不在内。
- **只有“生成FSD”路径能查 SAP**；对话任务在说“生成FSD”之前，目标系统只是占位值 `chat`。
- MCP 服务端暴露 128 个工具，含写操作（建对象、改源码、删对象）；应用层只放行读取类工具。

### 2.5 模型

组织默认模型是 SiliconFlow 上的 DeepSeek-V4-Pro（`openai_chat` 协议，默认开启深度思考）。实测：

| 现象               | 数据                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------- |
| 单个章节调用       | 94–225 秒，其中推理 token 占输出的 76–93%                                                             |
| 4 个调用并行       | 开启思考时每个都超过 300 秒；关闭思考时 4 个一共 40 秒                                                |
| 关闭思考           | `enable_thinking: false` 有效；简单章节格式无问题，最复杂的规范部分（6 小节一次写）出现 24 处格式错误 |
| 知识错误           | 退货、贷项、借项的凭证类别取值记错（标准是 H/K/L）；S/4 下仍写 VBUP                                   |
| 对话中被要求查系统 | 没有工具，输出了虚构的 `{"tool": "get_system_info"}`                                                  |

全局模型并发 `MODEL_CONCURRENCY = 4`，所有用户共用。

## 3. 暴露的问题（按根因归类）

1. **流程由程序主导，模型发挥不出来**。查什么、何时问、何时写，都由节点固定；模型无法在写的过程中发现缺口再去查、再回头改。
2. **工具不随对话可用**。最该少问基础问题的对话阶段，恰恰没有 SAP 工具；模型只能把技术判断推给用户，或虚构工具调用。
3. **输出格式过细**。自定义编写格式靠逐行解析；模型的自然写法（三级标题、块类型加限定语、依据后附说明）被判错并整章重写。10-11 改提示词后，首轮被退回的 36 处格式问题降到 0，但这是持续的维护成本。
4. **上下文被切碎**。文档按部分并行编写，各部分互相看不到，靠提纲约束一致性，再由收尾和审查找补。
5. **出错即停**。43 种错误码里多数会中断运行；用户只看到错误码，模型看不到原因。10-11 已改为内容检查按严重程度放行（见第 4 节），但流程本身的刚性还在。
6. **状态过重**。修改意见要走完整流程和两道确认；对话与文档割裂。
7. **生产级机制先于可用性**。租约、检查点、台账、预算、证据有效期、能力证据，每一项都合理，每一项也都产生过真实失败（LEASE_LOST、STALE_EVIDENCE、OUTCOME_UNKNOWN、BUDGET_EXHAUSTED、COMPATIBILITY）。
8. **模型因素未拆开**。慢主要来自深度思考与并发；知识错误来自模型本身。不把模型和架构分开验证，换架构也可能仍不满意。

## 5. 待讨论的问题

不预设答案，建议新会话逐项讨论：

1. **主导权**：继续程序主导的固定流程，还是改为模型主导的智能体循环（一个模型、一组工具、一份文档，由模型决定下一步）？
2. **状态**：需要哪些状态是“必须的”？候选的最小集合是“对话记录 + 文档版本 + 用户的采用动作”。确认、交付、审计能否不靠状态机，而靠工具的前置条件和日志？
3. **文档表示**：模型直接写 Markdown 文档（按标准样例的章节），导出时再转结构化或 Word；还是继续让模型写可解析的方言？内容模型 `fsd-report/1` 和渲染器放在哪一层？
4. **工具**：哪些工具随时可用（SAP 表结构、配置读取、对象搜索、附件、知识资料、向用户出选择题、读写文档、自检）？只读防护按工具类型做，还是按对象白名单做？
5. **用户修改**：大小修改都直接针对当前文档；模型如何判断影响范围、如何保留已确认内容？
6. **提问质量**：如何划清“客户决定”（业务口径、范围、取舍）与“顾问决定”（字段映射、实现方式）？是否要每批题目设上限并自查？
7. **知识**：是否需要一份按版本整理的 SAP 关键事实（S/4 状态字段、凭证类别取值等），还是全部依赖 SAP 实时查询？
8. **模型**：默认模型是否够用？按场景控制思考强度（分析、出题、审查保持深度思考，按提纲写章节可关闭）？并发如何配置？
9. **可靠性与审计**：哪些生产级机制现在就需要（只读防护、调用日志、成本上限），哪些可以推迟（检查点重放、提交台账、能力证据）？
10. **迁移**：如果转向，老链路怎么处理？AGENTS.md 要求不删历史数据、不改公开 API。

## 附录 B：查运行日志

界面上的“运行编号”是对话轮次 id（`fsd_v1_chat_turn.id`），由它找到 run，再看 operation（每次调用的耗时、token、错误）与 event（节点时间线、`output.rejected` 原文片段、`quality.issue`）。

```sql
-- :turn 为界面上的运行编号
SELECT t.run_id, t.input->>'action', t.input->>'prompt' FROM app.fsd_v1_chat_turn t WHERE t.id = :'turn';
SELECT kind, status, settled_at - created_at AS dur, reservation->>'actual_tokens' AS tokens, error->>'code' AS err
  FROM app.fsd_v1_operation WHERE run_id = (SELECT run_id FROM app.fsd_v1_chat_turn WHERE id = :'turn') ORDER BY created_at;
SELECT sequence, created_at, event_type, left(data::text, 400)
  FROM app.fsd_v1_event WHERE run_id = (SELECT run_id FROM app.fsd_v1_chat_turn WHERE id = :'turn') ORDER BY sequence;
```

本轮分析过的运行编号：`e712aa46-…`（300 秒超时）、`b1b1d7f5-9c55-4bf9-a33e-459569be4fe8`（30 分钟超时）、`fa40d5b5-4f8a-43fe-8512-0104aaa775ba`（对话中虚构工具调用）。
