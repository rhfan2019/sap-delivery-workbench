# ABAP 开发助手方向决策

> 2026-10-13 起草，2026-10-14 定稿。状态：**已确认**，第 12 节各项按建议执行；实施见[实施计划](../plans/2026-10-14-abap-dev-agent-implementation.md)。第 2 稿按用户对第 1 稿的答复重写：FSD 不作为前置条件，产物为单份程序，语法检查预留，增加从 SAP 同步代码。第 3 稿按用户对第 2 稿的答复修订：定位为开发新对象，按开发类型规定产物形态；开发顾问修改后的代码可上传文件或从 SAP 同步；代码版本记录所依据的资料；静态校验只报确定的问题。第 4 稿按用户对第 3 稿的讨论修订：明确工作模式（业务口径、技术方案、代码三类工作，由模型决定先出方案还是直接写代码）；首版只做基于 `YCL_FRH_REPORT` 的可执行程序；基类从 SAP 读取，读不到时用内置副本；系统指令取设计助手提示词与用户 GEM 提示词之长，各智能体提示词独立；与开发清单的开发类型、变更类型、开发对象衔接。第 5 稿：用户提供了基类源码，补充基类依赖与源码核对结论；系统指令草稿完成（5.1 节）；“台账”统一改称“开发清单”；用户提供了工具类与异常类源码，框架改为只把各类的定义部分交给模型（第 4 节）；用户确认 GEM 已过时，凡与用户提供的代码不一致处以代码为准；用户提供的示例程序 YTCA 用于核对框架约定（4.4 节）。本文沿用 [FSD 设计助手方向决策](2026-10-11-fsd-assistant-direction-decision.md)（下称“设计决策”）的原则，只记录开发助手不同之处。本文本身不授权改代码；第 9 节的模块拆分与新目录须先按 AGENTS.md 修订[目录与依赖契约](repository-contract.md)及检查规则后执行。

## 1. 决策

开发助手 `abap-dev-agent` 与设计助手同构：一个可配置的模型，配一份系统指令（业务分析方法与 ABAP 开发规范）、一组 SAP 只读工具和工作区工具，在对话中自主决定提问、查证、写方案、写代码和修改。系统只保存对话、版本和批注，不设阶段状态机，不设确认门，也不检查 FSD 的状态。

- **只开发新对象**，不承担改造已有程序。已有程序只作为参考资料读取。
- **首版只做可执行程序**：继承 `YCL_FRH_REPORT` 的报表程序，覆盖开发清单的开发类型“报表”（只读查询）和“功能”（可编辑 ALV、BAPI 写回、审批等）。增强与接口以后另行补充规范后支持。
- **输入不一定是 FSD**：可能只是一句自然语言需求、截图或附件。因此开发助手自带业务分析能力，没有 FSD 时由开发顾问充当设计者。

使用者统称**开发顾问**。

## 2. 工作模式

### 2.1 资料，而不是前置条件

开发助手的输入是一组资料，除开发清单外每一项都可以缺：

| 资料         | 来源                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| 开发清单     | 开发项的开发类型、变更类型、开发对象、事务码、名称与说明（见 2.8）             |
| FSD          | 设计助手的任一版本；业务顾问手工上传到开发项的文件；对话中上传的附件；或者没有 |
| 其他附件     | 需求文档、截图、样例数据、参考程序等                                           |
| 开发顾问说明 | 对话中的补充与纠正                                                             |
| SAP 事实     | 只读工具查到的表、字段、配置、FM/BAPI 签名、已有程序源码                       |
| 框架接口     | 由程序加载，不由模型查找（见第 4 节）                                          |

不要求 FSD 已定稿，不绑定 FSD 版本；开发顾问可以早于业务顾问开始工作。

### 2.2 三类工作，不是三个阶段

用户的 GEM 提示词把开发切成“业务分析 → 技术推演 → 代码生成”三个锁死的阶段。开发助手保留这三类工作的内容，去掉阶段锁：

| 工作         | 做什么                                                                                                                            | 写到哪里          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| 搞清业务口径 | 有完整 FSD 时只核对缺口与矛盾；没有 FSD 或 FSD 不全时，按设计助手的方法分析（生命周期、变体、粒度与状态、写操作、反向审查）并提问 | 开发方案·业务口径 |
| 写技术方案   | 数据量级与运行模式、取数结构（JOIN/CTE）、BAPI 与函数、权限（SRI）、DDIC 依赖、Clean Core 与 API 发布层级、结构化伪代码           | 开发方案·技术方案 |
| 写代码       | 按编码规范和基类生成单份完整程序                                                                                                  | 代码              |

GEM 用阶段锁和阻断短语控制节奏，是因为它没有工具、没有产物存储，只能靠用户确认推进。开发助手每一轮本来就会停下，“写完方案停下等审阅”自然就是一轮，不需要程序锁。

### 2.3 一轮怎么走

```text
资料（开发清单 / FSD / 附件 / 说明） → 澄清 → 补充或纠正 → 方案 → 代码 → 补充或纠正 → 修改 → …
        ↑                                                                         │
        └── 任意时刻：重新上传 FSD、开发顾问交回代码、加批注 ──────────────────────┘
```

每一轮由助手判断这一轮该做什么，做完即停下等待：

- 资料不足或互相矛盾，且只有开发顾问能定 → **提问**
- 信息足够 → **写或改方案与代码**，自动校验后停下
- 开发顾问只是在问问题 → **回答**

**先出方案还是直接写代码，由模型决定**（同设计助手的模式），系统指令给出判断标准：

- **先写开发方案，停下等审阅**：业务口径来自助手的推断（没有 FSD 或 FSD 不全），或仍有影响设计的未决事项。
- **方案与代码同一轮写出**：FSD 完整，且没有影响设计的未决事项。
- 开发顾问明确要求“直接写代码”时照做，推断的口径列入未决事项。

无论哪种，开发方案都先于代码写出或与代码同时写出，二者构成同一个版本。程序不设确认门，只在代码写入而开发方案为空时给出校验提示（第 7 节）。

### 2.4 澄清什么

- **实现层面**：用 BAPI 还是直接更新，加锁与提交策略；选择逻辑与数据量（是否分批、前台还是后台作业）；出错时如何提示、是否记日志、是否回滚；与已有程序的关系；FSD 没写清或前后矛盾之处。
- **业务层面**：没有 FSD 或 FSD 不全时，按设计助手的提问门槛问业务规则。

能在 SAP 中查到的不问，先查。编码规范已规定的（命名、SQL 写法、权限写法等）不问。

### 2.5 资料更新与冲突

1. **新 FSD**：对照当前版本所依据的资料（见 2.6“依据”），列出变化及其对方案和代码的影响。与对话中开发顾问的**明确决定**冲突的，必须提问，不得默认以新 FSD 为准而覆盖；不冲突的直接修改，并在回复中说明改了什么。
2. **开发顾问交回代码**（见 2.7）：保存为新版本，与上一版本比对，弄清开发顾问改了什么；之后的修改都基于这一版本，不得把开发顾问的手工修改冲掉。手工修改改变了业务口径或技术方案的，同步修改开发方案。
3. **优先级**：开发顾问在对话中的最新明确决定 > 最新资料 > 较早资料。助手依据的任何取舍都记入开发方案。

### 2.6 产物：开发方案 + 一份代码

**代码**：一个完整的可执行程序，目的是让开发顾问整份复制粘贴到 SAP。巨石代码，不拆 INCLUDE；业务逻辑封装在继承 `YCL_FRH_REPORT` 的局部类中。第一版不支持一个开发项多份代码。

**开发方案**：一份 Markdown，四部分：

| 部分       | 内容                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| 业务口径   | 没有 FSD 时写全：需求理解与假设、选择屏幕、输出、取数与判定、写操作、消息；有 FSD 时只写补充与差异              |
| 技术方案   | 2.2 表中“写技术方案”所列内容；允许伪代码                                                                        |
| 手工步骤   | 开发顾问在 SAP 中手工完成的：程序属性、文本元素与选择文本、消息类、DDIC 对象、事务码；必要时部署框架（第 4 节） |
| 假设与未决 | 关键假设、与 FSD 不一致之处及原因、未决事项                                                                     |

- **版本**：开发方案与代码一起构成一个不可变版本快照，可打“定稿”标签。来源分为“助手生成”“开发顾问上传”“SAP 同步”。
- **依据**：每个版本记录它所依据的资料清单及各自版本（哪一版 FSD、哪些附件、基类来自 SAP 还是内置副本）。资料更新时据此判断哪些变了（2.5 第 1 条）。
- **批注与修订**：开发顾问对代码行或开发方案加批注，助手逐条局部修改并回复，开发顾问标记解决（同设计决策 5.2 节）。修改证据同样由模型声明、程序独立比对。
- **批注锚定**：批注按原文片段锚定，行号只用于辅助定位。产生新版本后，程序在新版本中重新查找原文并迁移未解决的批注；找不到的标为“原文已变”，由开发顾问决定。

### 2.7 开发顾问修改后的代码交回

开发顾问在 SAP 中粘贴、调试、修改后，可以用任一方式交回：

1. **上传文件**：把代码复制到文本文件，作为对话附件上传。附件既可能是修改后的代码，也可能是参考资料；不明确时助手先问，确认后才保存为“开发顾问上传”版本。
2. **从 SAP 同步**：助手按开发清单登记的程序对象名（2.8）从 SAP 读取完整源码，保存为“SAP 同步”版本。

两种方式之后的处理相同：程序完整入库，计算与上一版本的差异，只把差异交给模型；模型需要上下文时按行范围读当前代码。原因是巨石程序常有上千行，而设计助手为模型设的 `getObjectSource` 上限是 400 行，不能让模型自己逐页读来同步。

读到的源码含 `INCLUDE` 语句时，不自动展开，提示开发顾问：开发助手的代码是单份的，请确认是否拆分过。

### 2.8 与开发清单的衔接

开发助手通过 delivery 的公开接口只读开发清单，不写开发清单。

| 开发清单字段 | 开发助手的处理                                                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 开发类型     | 报表、功能：支持。接口、增强：第一版不支持，助手在第一轮明确告知                                                                                                               |
| 变更类型     | 新增：支持。重构：在新对象上重写，旧程序作参考资料读取。优化（改已有程序）：超出范围，助手在第一轮明确告知                                                                     |
| 开发对象     | 取其中的程序对象（`R3TR PROG`）作为本份代码的对象名，用于 SAP 同步和代码中的 `REPORT` 语句。没有时由助手按命名规范提议，开发顾问到开发清单填写；有多个程序对象时由开发顾问指定 |
| 事务码       | 写入开发方案的手工步骤                                                                                                                                                         |

不支持的类型只由助手告知，界面不硬拦。

## 3. 范围

**第一版做：**上述工作模式；基于 `YCL_FRH_REPORT` 的可执行程序（报表与功能）；SAP 只读查询；读取已有程序源码作参考；从上传文件或 SAP 交回修改后的代码；程序端静态校验（第 7 节）；方案与代码查看、批注、版本差异、复制与导出。

**第一版不做：**

- **增强与接口**：待补充对应规范后支持。
- **改造已有程序**：只开发新对象。
- **语法检查**：预留。ADT 语法检查需要 SAP 中已存在的对象作为上下文，方案由用户另行验证后再定。代码中不预埋开关，接入时按当时方案增加校验步骤。
- **写入 SAP**：创建或修改对象、激活、传输请求、对象锁、ATC、单元测试。后期开放写入须另写决策，重新设计权限、传输和回滚。
- **应用内代码编辑器**：开发顾问的修改走 2.7 两种方式交回。

## 4. 框架

代码的架构锚点是基类 `YCL_FRH_REPORT`，局部类继承它；权限、日志、参数由基类提供的工具类完成。整套框架包括：

| 对象                    | 作用                                                                  |
| ----------------------- | --------------------------------------------------------------------- |
| `YCL_FRH_REPORT`        | 报表基类：运行流程、选择屏幕钩子、ALV 显示与事件                      |
| `YCL_FRH_UTIL_AUTH`     | 权限检查，生成影子范围表（SRI）                                       |
| `YCL_FRH_UTIL_LOGGER`   | 消息收集、弹窗显示、保存应用日志                                      |
| `YCL_FRH_UTIL_TVARVC`   | 读取 TVARVC 参数                                                      |
| `YCX_FRH_UTIL`          | 框架异常类                                                            |
| `YALV_DISPLAY_ALV_GRID` | 基类显示 ALV 所用的函数模块（`render_ui` 默认屏幕为 `SAPLYREP` 2000） |
| 框架消息类              | 基类与工具类使用的消息（如 002～010）                                 |

“部署框架”指在 SAP 中部署以上全部对象。函数模块与消息类的源码不在内置副本中，由用户自行部署。

### 4.1 加载哪一份

框架在目标 SAP 系统中不一定存在，开发顾问也可能没有可用的目标系统，因此由程序决定加载哪一份，不交给模型判断：

| 情况                             | 加载               | 版本依据记为               |
| -------------------------------- | ------------------ | -------------------------- |
| 有目标系统，且读得到框架各类     | SAP 中的源码       | 框架：SAP                  |
| 没有目标系统，或系统中没有这些类 | 模块内置的源码副本 | 框架：内置副本（内容摘要） |

- 按类逐个判断：某个类在 SAP 中读不到时，该类用内置副本。
- 每个会话加载一次。两份源码不一致时以 SAP 为准，内置副本只是兜底。
- 有目标系统但缺少框架对象时，程序在开发方案的手工步骤中加一条：先在 SAP 中部署框架。
- 内置副本已由用户提供，放在 [`apps/api/src/modules/abap-dev-agent/frameworks/`](../../apps/api/src/modules/abap-dev-agent/frameworks/)，每个类一个文件。

### 4.2 交给模型的是接口，不是全文

模型写代码需要两样东西：**签名**（方法名、可见性、参数、异常，错一个就是语法错误）和**行为约定**（如 `gt_out` 必须是 PUBLIC 内表）。二者分开提供：

| 部分     | 来源                                                                                                                               | 由谁维护 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------- |
| 签名     | 程序从加载的源码中截取类定义：基类保留 PUBLIC 与 PROTECTED 部分，其余类只保留 PUBLIC 部分；去掉 PRIVATE 部分、全部实现和签名注释框 | 程序     |
| 行为约定 | `report.md` 中“基类是架构的唯一依据”一节：运行流程、可重定义方法、基类已处理的事项、工具类用法                                     | 人工审阅 |

- **原因**：五个类的全文约 87 KB（约 2.5 万 token），截取后约 10 KB（约 3 千 token）。智能体每次工具调用都重发上下文，一轮常有数十次调用，全文会带来数十万 token 的额外输入；大段与当前任务无关的实现也会分散较弱模型的注意力。
- **签名由程序截取而不是人工总结**：人工总结会与源码脱节；程序截取对 SAP 源码与内置副本一视同仁，保持“以系统为准”。
- **行为约定由人工维护**：需要理解实现才能写对，且很少变化，适合审阅后固化在提示词中。
- 截取结果放在上下文前部的“框架接口”一节，利用提示词缓存。模型不需要自己查找，也不再输出 GEM 的“基类架构证明”。
- 内置副本保存完整源码，截取规则只实现一处。`YALV_DISPLAY_ALV_GRID` 只在基类 `display` 内部使用，报表不需要了解，不收录。

### 4.3 源码核对结论

据此修正 GEM 的描述，已写入 `report.md`：

- `select`、`process`、`prepare`、`display`、`build_alv_grid_fcat`、`build_alv_grid_paras`、`ref_fcat` 是 PROTECTED 方法；GEM 把 `select`、`process` 列为 PUBLIC，与源码不符。重定义时可见性写错会导致语法错误，这正是由程序加载源码的价值。
- `gt_out` 必须是子类的 PUBLIC 内表属性，基类在 `display` 中通过 RTTI 按名称查找，缺失时以 A 类消息终止。
- 参照 DDIC 字段的选择条件，选择文本由基类在运行时自动注入，手工步骤只需列出无 DDIC 参照的字段。
- 字段目录由基类从 `gt_out` 的类型自动生成，子类只在 `build_alv_grid_fcat` 中调整，可用 `ref_fcat( )` 引用单列；`MARK`、`LIGHT` 自动设为技术字段，`MARK` 为选择列。
- 双击、热点、录入变更等 ALV 事件在子类重定义后由基类自动注册。
- 后台作业（`sy-batch`）中 `display` 直接返回，不输出清单。
- **GEM 的权限检查范例与源码不符**：`check_authority` 只有一个异常 `check_failed`，GEM 范例写了 `no_authority`、`too_many_records`、`invalid_parameter` 三个不存在的异常，照写会出语法错误。源码还提供了 GEM 未提到的能力：单值参数传 `iv_parameter` 检查；`iv_table_field` 指定主数据表；`iv_actvt_value` 指定活动（默认 03 显示）；影子范围表上限 5000 条，可由 TVARVC 参数 `YFRH_UTIL_AUTH_MAX_RECORDS` 调整。
- 权限检查对区间和通配条件使用 `CL_AUTH_OBJECTS_TO_SQL` 生成授权条件，较旧的 SAP_BASIS 版本可能没有该类，实现时在目标系统上确认。
- 日志工具支持收集 BAPI 返回、弹窗显示和保存到 SLG1；TVARVC 工具适合存放“希望可配置、又不值得建配置表”的值。二者的用法已写入 `report.md`。

### 4.4 示例程序 YTCA

### 4.5 范例程序 YDEMO_FRH_0021

用户提供了简单报表 YDEMO_FRH_0021（采购订单执行情况清单，267 行、约 9 KB、约 3 千 token），**作为报表规范的完整范例**，放在 [report-example.abap](../../apps/api/src/modules/abap-dev-agent/prompts/report-example.abap)，实现时随 `report.md` 一起拼入系统指令。用户的方针是先用简单报表把智能体做出来，复杂情况（可编辑 ALV、写回、ALV 树等）以后逐步增加范例与规范。

范例第一版与规范有三处不一致，用户于 2026-10-14 修改代码并作出决定，规范随之修订：

## 5. 系统指令

系统指令以设计助手的 [system.md](../../apps/api/src/modules/abap-fsd-agent/prompts/system.md) 和用户经过检验的 GEM 提示词为蓝本，各取其长，独立成文，不与设计助手共用片段。

**取自设计助手：**

**取自 GEM：**

- 业务分析补充：数据量级与运行模式（前台在线 / 后台作业）评估；Clean Core 评估及 API 发布层级。
- 编码规范全套：命名矩阵（作用域 + 类型前缀、`GT_OUT` / `GT_DTL`、字段符号、`TY_` / `TS_` / `TT_`）；Clean ABAP 与 7.40+ 现代语法；SQL 范式（`SELECT FROM … FIELDS … WHERE … INTO`，禁 `SELECT *`）；禁用 `FOR ALL ENTRIES`；CTE 的使用边界；计算下推；`LOOP AT … GROUP BY`；表表达式容错；文本符号（`'…'(Fxx)` / `Mxx`）及序号稳定；FCAT 用 `VALUE`、不用宏；`select1` / `process1` 顺延命名加中文注释；魔法字符串加注释；默认值下沉到 `initialize`；类型组件注释；不写 ABAP Doc。

## 7. 校验

每次写入后自动执行，结果作为提示交给模型，不退回、不中断（同设计决策）。**只报确定的问题，拿不准的不报**，避免模型被误报带偏：

- **表与字段**：只核对 `SELECT … FROM` / `JOIN` 后的表名，以及源码中明确写出的 `表名-字段名`（表名须为 SAP 中存在的透明表或视图）。别名、结构、局部类型、内表组件不核对。复用设计助手的 DDIC 核对逻辑。没有目标系统时跳过。
- **文本与消息**：源码中的 `TEXT-xxx` 与 `'…'(xxx)`、选择屏幕参数、消息号与开发方案手工步骤中列出的一致。
- **完整性**：没有截断，`FORM` / `METHOD` / `CLASS` 等块配对；没有省略号占位。
- **编码规范中可确定判断的规则**：出现 `FOR ALL ENTRIES`、`SELECT *`、`AT NEW`、ABAP Doc（`"!`）；`INTO` 前置的旧版 SQL；`INITIALIZATION` 块含对象创建与 `initialize( )` 调用以外的语句；`TYPES` 名称带作用域前缀；`SELECT-OPTIONS` 没有对应的 `xxx1` 影子范围表。命名前缀的其余规则保留为模型自查，验证误报情况后再决定是否纳入。
- **产物配对**：代码写入时开发方案为空。
- 语法检查接入后加入此处。
