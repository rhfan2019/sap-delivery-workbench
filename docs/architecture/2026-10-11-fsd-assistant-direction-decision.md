# FSD 设计助手方向决策

> 2026-10-11。状态：已实施（2026-10-12 更新）。按[重构实施计划](../plans/2026-10-11-abap-fsd-agent-refactor.md)完成清除与重建，[DEV-0031 端到端测试](../plans/2026-10-12-abap-fsd-agent-e2e-test.md)有条件通过；DEV-0024 验收与多模型批量测试待完成（见第 9 节）。本文记录对[方案审视](2026-10-11-fsd-assistant-approach-review.md)第 5 节的讨论结论，是后续契约修订和实施计划的依据。本文本身不授权改代码；第 6 节涉及的删除和 API 变更，须先按 AGENTS.md 修订[目录与依赖契约](repository-contract.md)及检查规则后执行。

## 1. 决策

FSD 设计助手由**程序主导的固定流程**转为**模型主导的智能体**：

> 一个可配置的模型（兼容常见大模型，按客户条件切换），配一份系统指令（方法论与交付标准）、一组 SAP 只读工具和文档编辑工具，在对话中自主决定提问、查证、写稿和修改。系统只保存对话、文档版本和批注，不设阶段状态机。程序只负责边界与确定性校验：只读、花费上限、自动校验、SAP 事实核对、修改差异比对。在现有项目中完全重构：v1 的后端、前端、表结构与数据全部清除，不保留版本号层级，不带历史负债。

## 2. 依据

1. **投入产出**：v1 连续开发 4～5 天、约 8,900 行、23 次提交，多数修补是让模型输出适配程序约束，仍不能稳定跑通一个简单报表。问题在结构，继续修补难以收敛。
2. **任务本质**：顾问写 FSD 是“需求 → 澄清 → FSD → 修正 → 需求”的循环，过程中会跳到任意一步。固定节点和阶段状态机假设的是单向流水线，每次跳回都要新增状态和规则。
3. **对照实证**：用户的 Gemini GEM（Gemini 3.1 Pro，仅系统指令 + 对话，无状态控制、无 SAP 工具）在 5～10 分钟内完成同类 FSD，质量满意；Codex / Claude Code 的经验相同。
4. **趋势**：模型能力持续提升，写死的流程不会随之变好，反而限制更强的模型。换模型即可受益的架构长期回报更高。

## 3. 两点修正（避免重复 v1 的错误）

**v1 的失败不全是架构造成的。**以下原因与架构无关，新方案同样要解决，并在验证中单独拆开：DeepSeek 深度思考单次调用慢、并发时超时；SAP 白名单过窄、读不到后台配置；对话阶段没有工具。

**模型主导不等于程序不管。**程序控制分两类，态度相反：

| 类型                             | 例子                                                                     | 态度           |
| -------------------------------- | ------------------------------------------------------------------------ | -------------- |
| 控制模型**怎么想、下一步做什么** | 固定节点、阶段状态机、确认门、输出方言、格式退回重写                     | 去掉           |
| 守住**边界和确定性事实**         | 只读工具、花费上限、写入后自动校验、SAP 核实字段存在、修改差异比对、版本 | 保留，甚至加强 |

判断标准：**模型做不可靠、而程序能做得可靠的事，才交给程序。**

## 4. 约束

- **模型**：兼容所有常见大模型（Gemini、Claude、GPT、DeepSeek、Qwen、Kimi 等），按每个客户的条件动态修改配置，不限定厂商或产地。模型必须可配置切换；客户条件下的模型质量差一些也要先出成果，后续靠换模型提升。（2026-10-13 勘误：此前写作“客户硬性要求国产模型，不能使用 Gemini、Claude、GPT”，表达不准确，以本条为准。）
- **设计必须适应较弱模型的弱点**：长链条工具调用易跑偏或虚构调用、单次输出长度有限。因此每轮有明确终点、工具少而清楚、弱模型容易遗漏的检查由程序在固定时机自动执行。

## 5. 目标形态

### 5.1 一轮对话

Agent 只有一个目标：输出 FSD。用户发一条消息到 Agent 停下等待，称为一轮：

```text
用户消息（需求 / 补充信息 / 修改意见 / 批注）
  → Agent 判断：离写出或改好 FSD 还缺什么
  → 推导需要核实的 SAP 对象清单，批量查询；必要时补查
  → 缺的是只有客户能定的事 → 向用户提问，停下
     信息足够             → 写或改 FSD，自动校验后停下
     用户只是提问         → 回答，停下
```

“先推导对象清单、逐一查询、全部完成后统一思考”是默认工作方法，写入系统指令，并提供批量查询能力减少轮次。写作中发现缺口时允许补查。只有验证显示模型在连续工具调用中系统性跑偏时，才由程序固定为“先查证、再写作”两步，每步内部仍由模型自主（见第 8 节）。

### 5.2 已确定的设计要点

| 项       | 决定                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 主导权   | 模型主导，无阶段状态机、无确认门                                                                                 |
| 状态     | 只保存产物：对话记录（含工具调用）、文档版本（不可变快照）、批注（未解决 / 已解决，由用户控制）                  |
| 确认     | “确认 / 定稿”是给某个版本打标签；定稿后仍可修改，修改产生新版本                                                  |
| 生成     | 严格串行；初稿尽量整份生成，单次输出写不完则在同一上下文中顺序分章续写；不并行                                   |
| 文档表示 | 模型直接写 Markdown，章节对照标准样例 ISC001；不再使用可解析的编写方言                                           |
| 修订     | 参考 Claude 的标记与回复：用户对原文加批注，模型逐条局部修改并回复，用户标记解决；改动大时由模型决定重写整章     |
| 修改证据 | 模型每轮声明修改清单（批注、位置、改前、改后、理由）；程序独立计算版本差异并比对，标出“未声明修改”和“声明未落实” |
| 校验     | 程序提供校验工具，并在每次写入后自动执行；结果只作为提示交给模型，不退回、不中断；修不好的问题列入未决事项       |
| token    | 修订只改受影响部分；同一会话的系统指令与文档前缀使用提示词缓存                                                   |

### 5.3 SAP 工具

SAP MCP 只读查询是相对 GEM 的重大提升，用于抑制模型的知识性幻觉，**必须引入**，且对话全程可用。

- **暂定能力**（后续按需扩展）：表和结构定义、域固定值、表内容（限制行数、必须指定字段）、功能模块与 BAPI 参数、后台配置、对象搜索、源码读取。
- **直接使用 MCP 原生工具**，不另行封装；由系统指令说明何时用哪个工具。abap-adt 共 126 个工具，按“只读且与 FSD 相关”筛选后暴露约 15 个：`searchObject`、`findObjectPath`、`objectTypes`、`ddicElement`、`ddicRepositoryAccess`、`tableContents`、`runQuery`（仅 SELECT）、`getObjectSource`、`objectStructure`、`classComponents`、`findDefinition`、`usageReferences`、`abapDocumentation`。写操作、代码执行（`runClass`）、调试、跟踪、ATC、Git、传输请求类工具不暴露。缺什么再放开对应的原生工具。
- **后台配置**指 SAP 系统配置，例如销售凭证类型的参数（哪些订单类型是退货、贷项、借项）。实现方式是读配置表内容，由模型决定表、字段和条件；不再依赖 v1 预先登记的 SQL 模板。
- **对象范围**：去掉对象白名单，任何对象都可查询。
- **只读**：本次只向模型暴露预置的只读能力，写操作不进入工具列表，服务端按工具类型拒绝其他调用。SAP 用户权限这一最后防线后续在 MCP 中实现，本次不处理。
- **事实核对**：自动校验时，程序提取 FSD 中的表名、字段名和域取值，到 SAP 核实是否存在，不依赖模型记忆。
- **依据**：FSD 中的事实区分“已在 SAP 核实”和“推断”；查询记录即证据链，不再使用 v1 的证据有效期机制。

## 6. 重构方式

在现有项目中完全重构，轻装上阵。用户于 2026-10-11 明确决定以下事项，它们改变了 AGENTS.md 中“不删除历史数据、不改变公开 API”的默认约束，须先修订契约再执行：

- **统一命名、不保留版本层级**：FSD 设计助手统一命名为 `abap-fsd-agent`（后端模块、前端 feature、共享契约、提示词、API 路径 `.../development-items/:itemId/abap-fsd-agent`、表名前缀 `abap_fsd_agent_`）；开发助手预留 `abap-dev-agent`，实现前不建空目录。不再使用 design-assistant、fsd、fsd-agent、fs-workspace 等同义名称。今后只有一个版本，不设版本目录、版本化路径或表名，旧路径不保留转发或 410 壳。
- **表与数据**：历史各代助手的表定义与数据全部删除（`fsd_v1_*`、`gem_fsd_v2_*`、`fsd_agent_*`、fs-workspace 的 `fs_*` 系列、`item_work_version` 等，以及 LangGraph 的 `fsd_checkpoint` 模式），具体清单见实施计划。已执行的迁移文件不改写，以新增迁移删除旧表并建新表。不做备份。delivery 自有的 FS 台账表（`fs_draft`、`fs_version`）不属于助手，保留。
- **后端**：design-assistant（LangGraph 链路）、agent-runtime（旧 abap-fsd-agent 引擎）、fs-workspace（功能规格工作区）、item-workspace 中的开发助手后端全部删除（开发助手尚未使用过），新智能体从零编写。
- **前端**：现行设计助手前端（开发项工作区设计阶段的界面与其对话、附件、决策卡片等组件）用户认可，**保留**并迁入 `features/abap-fsd-agent`，改接新 API；文档区由结构化编辑器改为 Markdown 文档、批注与版本。删除“FS助手测试”菜单与页面、运行诊断页、fs-workspace 前端及未被引用的旧组件。设计与开发共用同一界面，开发阶段入口在 abap-dev-agent 实现前隐藏。
- **智能助手日志分析**：基于新表重构，优先级靠后；另一会话中尚未提交的 `insights-*` 改动（含其对 `app.mjs`、`policy.mjs`、`navigation.ts`、`router/index.ts` 的修改及迁移 `1791676800000`）放弃，在编码开始前清除。
- **所有历史版本一律清空**：旧设计助手的 410 边界（`work/design/agent`、`gem-fsd-v2`、`/api/admin/abap-fsd-agent`）、一代 FS 助手 fs-workspace、“FS助手测试”及其后端、相关契约（含 `agent-runtime/fsd/v1`）、测试、工具、脚本与部署配置一并删除，不保留任何 v2、v3 等版本痕迹。
- **只沿用内容资产，不沿用代码负债**：系统提示词第一～九部分（改写后使用）与 10-11 的格式经验；SAP 连接登记与连通性配置；标准样例 ISC001 与 DEV-0024；模型配置管理（含组织默认模型）。SAP 适配器、渲染器、`fsd-report/1` 是否沿用，在实施计划中逐个评估，以新形态需要为准。

## 7. 风险与应对

| 风险                         | 应对                                               |
| ---------------------------- | -------------------------------------------------- |
| 连续工具调用跑偏、重复、虚构 | 工具少而清楚；批量查询；每轮调用次数上限；重复检测 |
| 输出截断                     | 校验发现缺章后续写缺失部分，不整份重写             |
| 质量波动、不可复现           | 完整日志与版本；用户批注修正                       |
| 排查困难                     | 记录每次模型与工具调用的输入输出                   |

## 8. 改判条件

若验证中“客户所用模型 + SAP MCP”在连续工具调用上系统性跑偏（多数轮次出现重复或虚构调用），增加轻量两步结构：程序固定“先查证、再写作”，每步内部由模型自主。不存在退回 v1 形态的合理场景。
