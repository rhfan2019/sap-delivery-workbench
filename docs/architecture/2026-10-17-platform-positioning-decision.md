# 平台定位方向决策

> 2026-10-17 起草，同日定稿。状态：**已确认**，第 10 节为用户对待确认问题的答复，正文已按答复修订。同日补充第 5 节第 6 条（测试数据例外）；项目主数据、权限与项目 SAP 系统的细化设计见[项目主数据、权限与设置菜单设计](../specs/project-access-admin.md)。本文记录 2026-10-17 对平台立足点的审视与讨论结论：平台定位为**实施方内部的交付生产工具**，不做客户的项目管理系统。本文本身不授权改代码；第 8 节涉及的表结构、API 与目录变更，须先按 AGENTS.md 修订[目录与依赖契约](repository-contract.md)及检查规则后执行，且不得借此删除历史数据或改变其他模块的公开 API。

## 1. 决策

> 本平台是实施方团队内部使用的 SAP 交付生产工具：顾问用它完成设计（FSD）、开发、测试等交付工作，降低实施成本。平台、智能体、提示词、开发框架和评测资产归实施方所有，部署在实施方受控环境；交给客户的只是产出物（FSD、代码、测试资料、开发清单导出），不是工具本身。

- **不做客户的项目管理系统**：需求池、RAID、变更请求、缺陷、传输请求、签核等甲乙双方共同管理的事项，以客户指定的工具为准（Solman/ChaRM、Jira、Excel 等）。平台只在需要时导出或对接，不承担“项目主人”的角色。
- **开发清单是团队内部的生产台账**：用于派活、跟踪各阶段进度、进入各助手；对客户以 Excel 导出交付。
- **只部署在实施方环境**（第 5 节）；客户内网部署暂不考虑（第 6 节）。

## 2. 背景与依据

1. **原立足点的矛盾**：原设计按“实施公司 → 客户 → 项目”组织数据（`organization → customer → project`），隐含“平台是项目的主人”。真实的 SAP 项目以客户为中心，客户出于数据安全会要求项目系统部署在客户环境；而一旦部署到客户环境，FSD、开发、测试助手这些核心资产就脱离了实施方控制。两种诉求在“项目系统”这个定位下无法同时满足。
2. **初衷是团队加速**：平台的出发点是让实施团队更快、更省地交付。这属于实施方的生产工具，不需要成为客户的项目系统。
3. **客户真正关心的是数据，而不是工具放在哪里**：顾问本来就通过 VPN 用自己的电脑访问客户 SAP，在自己的环境里写 FSD 和代码。客户的关注点是：访问了哪些系统、数据交给了谁（尤其是哪个大模型）。这些可以用工具内的控制和合同解决（第 5 节）。
4. **合规的 AI 工具是卖点**：与顾问私下把代码贴进各种聊天机器人相比，一个只读、不连生产、可选客户批准的模型、可审计的工具，对客户的数据安全更有利。
5. **护城河不在提示词文本**：提示词随模型更替很快过时（用户的 GEM 提示词已过时即为一例）。难以复制的是持续迭代能力：端到端测试用例、批量评测记录、跨项目样本、对各家模型弱点的处理经验，以及会用这套工具的团队。这些只留在实施方内部。

## 3. 边界

| 平台做                                              | 平台不做                                                         |
| --------------------------------------------------- | ---------------------------------------------------------------- |
| 开发清单（内部生产台账）、各阶段负责人与进度        | 客户方参与的需求池、Gap 签核、RAID、变更请求、缺陷管理           |
| FSD 设计、ABAP 开发、后续顾问测试与 IT/用户测试助手 | 传输请求管理（以 Solman/ChaRM 或客户流程为准，平台只记录 TR 号） |
| SAP 只读查询（开发、测试系统）、代码校验            | 连接 PRD；向 SAP 写入（测试数据例外，见第 5 节第 6 条）          |
| 产出物导出（FSD、代码、开发清单 Excel、测试资料）   | 作为客户的长期项目系统运营                                       |
| 面向客户的数据访问审计导出、项目人工归档            | 客户内网部署                                                     |

客户方人员目前不是平台用户，确需客户查看时以导出物提供。以后如有需要，可以把平台开放给客户：为客户增加用户，通过权限控制其可见范围与可用功能（第 6 节）。

## 4. 资产与产出物的归属

| 类别     | 内容                                                                      | 归属   | 去向                                      |
| -------- | ------------------------------------------------------------------------- | ------ | ----------------------------------------- |
| 方法资产 | 智能体程序、系统指令与提示词、`YCL_FRH_REPORT` 等开发框架、评测用例与记录 | 实施方 | 只在实施方环境                            |
| 项目数据 | 开发清单、对话、SAP 查询记录、附件                                        | 客户   | 在平台内无限期保留，可人工归档（第 7 节） |
| 产出物   | FSD、开发方案与代码、测试资料、开发清单导出                               | 客户   | 按合同作为交付物交给客户                  |

- **开发框架**：`YCL_FRH_REPORT` 已在多个项目实践，客户普遍接受，作为实施方框架随代码部署到客户 SAP 系统是正常交付。客户最多要求改基础类名称，平台按项目配置类名（第 8.6 节），不另做“客户规范优先”的规范层。
- **跨项目沉淀**：平台是内部工具，跨项目沉淀的 FSD 范例、代码样本和评测用例暂时完整保留，不做去标识处理，具体规则以后再定。
- **合同**：数据处理条款约定访问范围与使用的模型；知识产权条款约定产出物归客户、工具与方法归实施方。

## 5. 部署与数据安全

平台部署在实施方受控环境（现有 `infra/production` 方案），通过 VPN/专线访问客户 SAP。以下措施让客户可以接受“项目数据经过实施方工具”，须由程序强制执行，不能只写在提示词里：

1. **只连 DEV 与 QAS**：智能体工具层已限制为 DEV/QAS（`agent-core` 的 `SAP_ENVIRONMENTS`），但 SAP 连接配置仍允许登记 PRD（`sap` 模块 `environments`、`project_sap_config.environment`）。去掉 PRD 配置，避免在平台内保存生产凭据。
2. **不做数据分级**：SAP 表数量巨大，按表分级或逐表开放的配置工作量大、收益小。SAP 只读工具维持现状（只读、只允许 SELECT、不设对象白名单），不按表限制读取内容。
3. **SAP 账号可追溯到人**：优先使用顾问本人的 SAP 账号（现有的用户级 SAP 配置），项目级共享账号只作后备，并在审计中记录实际操作人。
4. **模型由客户条件决定**：每个项目可指定允许使用的模型（客户批准的云模型、客户提供的 API Key、或经专线调用的客户私有化模型）。现有模型配置按组织设定默认值，需增加项目级的模型限定。
5. **面向客户的审计**：可按项目导出“谁、何时、查询了哪个 SAP 对象或表、哪些内容发给了哪个模型”，供客户安全部门复核。现有审计日志面向平台运维，需补充这一视角。
6. **测试数据是唯一的写入例外**（2026-10-17 补充）：为测试案例在测试系统创建业务单据，只限项目登记的测试系统，需要 `sap.test_data:create` 权限，每次执行前由用户逐次授权并留下运行记录（契约 3.4）。除此之外平台不向 SAP 写入。

## 6. 客户内网部署与开放给客户：暂不考虑

平台只定位为实施方内部的生产工具，不做客户内网部署，不为此准备加密许可包、离线安装与升级。

以后如有需要，开放的方式是在实施方环境中为客户增加用户、通过权限管理，而不是把平台部署到客户环境。届时另立方案，确定客户用户的角色、可见范围以及是否开放各助手。

## 7. 项目结束

- **客户付费续用**：保留系统与数据，按服务约定继续使用。
- **客户不续用**：用导出程序把产出物打包，作为项目交付物交给客户：开发清单 Excel、各开发项的 FSD 定稿与历史版本、开发方案与代码、测试资料、附件清单。导出物不包含系统指令、提示词、评测资料或平台程序。
- **数据留存**：项目数据无限期保留，不自动清除。平台提供人工归档：由管理员把结束的项目归档，归档后只读、默认不在工作区列表中显示，可查询与导出。现有项目状态已有“已归档”（`project.status = 'archived'`、`archived_at`），在此基础上补齐归档后的只读与显示规则。
- 导出程序需支持按项目整批导出、文件结构稳定、可重复执行。

## 8. 对现有设计的影响

本节只列方向，具体改法写入实施计划，并先修订契约。

### 8.1 组织、客户与项目

- 组织（`organization`）回到“实施方自身”的含义；平台不是多实施方 SaaS，不需要为多家实施方隔离数据。
- 客户（`customer`）表和客户管理界面保留，现有“外部客户 / 自有客户”的区分不变（自有客户用于实施方内部项目）。
- SAP 版本与部署形态（ECC、S/4HANA 本地、RISE 私有云、公有云等）登记在**项目**上，而不是客户上：同一客户的不同项目可能面对不同系统。各助手据此提示适用范围。
- 项目成员仍是实施方人员；不引入甲方角色。

### 8.2 SAP 连接

- 去掉 PRD 环境（第 5 节第 1 条）。
- `sap_system_grant` 等现有结构暂不调整，留待以后开放给客户时一并评估（第 6 节）。

### 8.3 模型

- 增加项目级的模型限定（第 5 节第 4 条）；助手运行时只能使用该项目允许的模型。

### 8.4 审计与数据生命周期

- 增加项目维度的 SAP 访问与模型调用导出（第 5 节第 5 条）。
- 增加产出物导出与项目人工归档（第 7 节）；不做自动清除。

### 8.5 开发清单

- 定位为内部生产台账，现有字段与功能保留。
- “业务 Owner”保持文本，客户方人员不是平台用户，这与本定位一致。
- 可增加“传输请求号”登记字段，只记录不管理（可先用自定义列）。

### 8.6 开发框架

- `YCL_FRH_REPORT` 及其工具类、异常类的名称按项目可配置：开发助手加载框架、生成代码与校验时使用项目配置的类名，内置副本按配置替换类名。

### 8.7 部署

- `infra/production` 的腾讯云方案即平台的部署方案，补充访问客户 SAP 的 VPN/专线说明与第 5 节的数据安全措施。

## 9. 2026-10-17 审视问题的处理

审视时以 SAP 实施项目经理视角列出 22 个问题，按本定位处理如下：

| 问题                                                 | 处理                                                                  |
| ---------------------------------------------------- | --------------------------------------------------------------------- |
| 数据层级与客户内部署冲突                             | 采纳：组织即实施方；客户表与管理界面保留，SAP 版本等登记在项目（8.1） |
| 部署方案只考虑实施方云                               | 与本定位一致：只部署在实施方环境，客户内网部署暂不考虑（第 6 节）     |
| SAP 数据发给外部模型                                 | 采纳：项目级模型限定、审计导出；不做数据分级（第 5 节）               |
| SAP 连接越界（PRD、共享密码、授权方向）              | 采纳：去掉 PRD、优先个人账号；系统授权暂不调整（8.2）                 |
| 无企业统一身份登录                                   | 改为实施方内部需要，不再是客户硬性要求；按实施方情况另定，暂不处理    |
| 项目内无角色                                         | 只需实施方内部角色，按实际需要另行评估；开放给客户时再设计客户角色    |
| 业务 Owner 存文本                                    | 与本定位一致，保留                                                    |
| 只能有一个实施方                                     | 分包人员作为实施方成员加入项目；不做多实施方隔离                      |
| 只覆盖部分 RICEFW                                    | 按助手路线逐步扩展，属于生产工具范围                                  |
| 追溯链、传输请求、RAID、变更请求、签核               | 不做，以客户指定工具为准；传输请求号可在开发清单登记（8.5）           |
| 进度口径                                             | 内部台账需要时再改，不在本决策范围                                    |
| 未区分客户 SAP 版本与部署形态                        | 采纳：登记在项目（8.1）                                               |
| 开发规范以实施方框架为准                             | 不采纳：框架已获客户普遍接受；只做类名配置（8.6）                     |
| 核心资产外泄                                         | 采纳：只部署在实施方环境，资产不出（第 4、6 节）                      |
| 项目结束后的处理                                     | 采纳：续用，或导出产出物交付；数据无限期保留、人工归档（第 7 节）     |
| 分散部署的升级、高可用、甲方视角审计、模型按组织配置 | 不分散部署，升级与高可用由实施方统一负责；审计与模型见第 5 节         |

## 11. 实施顺序

1. 修订[目录与依赖契约](repository-contract.md)：登记本决策，明确各模块在新定位下的职责变化。
2. SAP 连接去掉 PRD；开发框架类名配置。改动小、风险低，先做。
3. 项目上登记 SAP 版本与部署形态；项目级模型限定。
4. 项目维度的审计导出；产出物导出程序；项目人工归档（只读与显示规则）。
5. 部署文档补充访问客户 SAP 的说明与数据安全措施。

每一步单独提交，按契约完成相关验证。
