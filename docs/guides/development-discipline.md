# 项目开发纪律

> 状态：现行，2026-10-29 用户要求建立。适用于本仓库的所有开发（人工与智能体）。与 [AGENTS.md](../../AGENTS.md)、[目录与依赖契约](../architecture/repository-contract.md) 冲突时以契约为准；本文把散在各处的做法收成一份可检查的清单，新增约定时改本文。

## 1. 先文档，后代码

- 改行为、界面或接口之前，先改对应的规格（`docs/specs/`）或设计规范（[DESIGN.md](../specs/DESIGN.md)），再改代码；用户确认的决定在文档里写明“用户 YYYY-MM-DD 确认”。
- **文档与实现严格一致**：同一次提交里同时改代码与文档；发现两者不一致，先改成一致再做别的。规格里的“实现”表、页面清单、批次状态都要跟着改。
- 未完成事项只登记在[待办与问题清单](../plans/backlog.md)（发现的问题、未被采纳的建议、做了一半的事都加一行）；修复后写上提交号。
- 每条工作线一份交接文档（`docs/plans/*-handover.md`），按 AGENTS.md 的固定结构持续更新；运行方法写在[运行指南](agent-operations.md)，交接文档只放链接。

## 2. 分支、提交与推送

- 只在 `main` 上开发，不建分支；检查通过后自行提交并推送。
- 提交信息用英文：`类型(范围): 一句话`，正文说明为什么改；修复待办项时在标题或正文写编号（如 `BUG-007`）。待办清单补提交号单独提交（`docs(backlog): … done in <hash>`）。
- 只提交自己的改动：不碰别人未跟踪的文件；Prettier 只格式化自己改过的文件，不对目录运行。
- 不重写已推送的历史，不跳过钩子。

## 3. 每次提交前的检查

| 改动               | 必须通过                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------- |
| 任何改动           | `npm run check:architecture`、`npm run check`                                                   |
| 前端与共用代码     | `npm run test:unit`                                                                             |
| 接口、数据库、权限 | `npm run test:integration`；新增写接口为缺权限（403）与范围外项目（404）各写一条集成测试        |
| 页面流程           | 相关的 e2e（`tests/e2e/`），并在内置浏览器里实际操作（浅色、深色，1280 / 1440 / 1920 / 390 宽） |
| 数据库结构         | 新迁移放 `database/migrations/`，只增不改已发布的迁移；初始化与升级都能跑通                     |

- 测试自己启动的 Vite 一律在 `NODE_ENV=test` 下运行（`npm run test:*` 已设置；单独运行一个测试文件时手动加），否则会替换开发服务的依赖打包缓存，正在用的页面打不开（BUG-008）。
- 失败如实报告；与本次改动无关的既有失败也要修复或登记待办，不能带着红色测试提交。
- 不临时绕过检查器；规则需要改变时，先改契约与检查规则，再迁移代码。

## 4. 界面一致性

- 只用 `theme.css` 的令牌，不新增颜色值；组件与页面形态以 DESIGN.md 为准。
- 同类页面用同一套共用部件，页面不另写同类样式：设置区的列表一律是“概要 → 工具行 → 两行表格 → 说明”，新增与编辑在右侧抽屉（DESIGN.md 第 5、6.2 节，`features/settings`）；确认、登录、复制等一次性小操作才用对话框。
- 新增部件前先找现有部件；两个页面写了相同的样式，就收进共用样式。
- 文案用中文、简短、说清后果；不可撤销的操作在确认框里写明影响范围。

### 4.1 表格抽屉页

“表格加右侧抽屉”的页面（设置区的列表、团队与干系人、计划与健康、开发清单）一律按下面的规则（用户 2026-10-30 要求），详见 DESIGN.md 第 5 节“抽屉”：

- **打开方式决定初始状态**：点表格行打开的抽屉**只读**；点行尾“编辑”按钮打开的直接进入编辑；“新建 / 登记 / 添加”打开的直接编辑。没有修改权限的人点行也能打开只读抽屉，只是没有“编辑”。
- **只读时**：字段的位置与编辑时相同，值显示为文字（无边框、无底色），空值显示“未填写”；必填星号、填写说明和只与修改有关的提示不显示。标题是记录名称，说明是它的标识；底栏右侧是“编辑”主按钮（有权限时）和只读时可用的操作（如“打开设置”“复制”）。
- **原地切换**：点“编辑”在同一个抽屉里切换为控件，焦点落在第一个可改的字段，底栏变为“取消”“保存”。“取消”放弃修改回到只读（新建时关闭抽屉）；保存成功后回到该记录的只读状态，抽屉不关闭。抽屉已只读打开时再点同一行不变，点该行的“编辑”切换为编辑。
- **字体一致**：字段名与值都用常规体，字段名靠 `text-2` 灰色区分，只有抽屉标题、分组标题和卡片标题加粗；以文字显示的值用 `.s-value`，与输入框里的文字对齐（DESIGN.md 第 5 节“抽屉”的字体表）。
- **离开前询问**：有未保存的修改时，切换到另一行、关闭抽屉、离开页面或关闭标签页先询问（`useDrawerLeave`）。
- 抽屉里自带保存的小表单（如用户的企业级角色分配）和一次性操作（重置密码）不受只读影响；删除等不可撤销的操作仍放在行尾 ⋯ 菜单。
- **实现**：设置区的抽屉用 `features/settings` 的 `SettingsDrawer`（`reading`、`editable`、`edit` 事件）与 `.s-fields` 字段组；开发项详情抽屉按同样规则实现自己的卡片布局。新增表格抽屉页必须照此实现，e2e 覆盖“点行只读 → 编辑 → 取消”。

## 5. 对象的全生命周期

每类业务对象都必须有完整的生命周期操作：**新建、查看、修改、停用或归档、删除**。不提供某个操作必须有理由，并登记在下表的“说明”里；新增对象时在表中加一行，并在同一次提交里实现表中承诺的全部操作（接口、权限点、界面入口、审计与测试）。

规则：

- **删除前检查引用**：被其他数据引用的对象不能直接删除，改为停用或归档，接口返回 409 并说明原因。
- **停用与归档可见、可恢复**：列表默认只显示在用的，筛选能看到停用 / 归档的；可恢复的提供“启用 / 恢复”。项目归档是单向的（平台定位决策：项目数据无限期保留、人工归档）。
- **不可撤销的操作**放在行尾 ⋯ 菜单，红色，先确认并写明影响；不放在抽屉里。
- **写审计**：创建、修改、停用、归档、删除都写审计日志（不含敏感内容）。
- **权限**：每个操作都经 `access` 模块按权限点校验（见 [项目主数据、权限与设置菜单设计](../specs/project-access-admin.md)）。

## 6. 数据与运行安全

- 本机 `.env`、`.runtime` 中的凭据与附件、数据库卷和用户备份受保护，不做批量清理；测试用 `.runtime/fs-tests.env` 指向的独立数据库。
- 不往用户自己的助手对话里发测试消息；重启服务前确认没有运行中的助手轮次（[运行指南](agent-operations.md)第 1 节）。
- 测试账号取 `.env`，不把密码写进聊天、文档或提交。
- 在内置浏览器里验证时不保存真实数据，除非任务就是改数据。

## 7. 完成的定义

一项改动完成，要同时满足：

1. 规格、设计规范与代码一致，用户确认的决定写在文档里；
2. 第 3 节对应的检查全部通过，并在浏览器里实际看过；
3. 新对象或新操作满足第 5 节，生命周期表已更新；
4. 待办清单与交接文档已更新（新问题登记、已修复写提交号）；
5. 已提交并推送到 `main`。
