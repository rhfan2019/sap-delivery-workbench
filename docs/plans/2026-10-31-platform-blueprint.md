# 平台蓝图：从“开发加速”到“SAP 实施加速”

> 2026-10-31 起草。状态：**草案，待用户确认**（第 6 节列出需要拍板的事项）。本文只做规划，不授权改代码；确认后再按 AGENTS.md 修订契约、DESIGN.md 与权限目录，并拆成实施计划。待办见 backlog FEAT-018。

## 0. 一句话

平台现在是“开发组长的开发工作台”，下一步要成为“**实施团队的交付物工厂**”：SAP Activate 每个阶段要交出的东西（方案、配置、FSD、代码、测试、迁移、切换、培训），都在平台里由助手协助产出、在台账里跟踪、在工作台上被看见。边界不变，仍然遵守[平台定位方向决策](../architecture/2026-10-17-platform-positioning-decision.md)：只服务实施方内部，不做客户的项目管理系统。

## 1. 现状诊断

### 1.1 菜单（信息架构）

现有四个模块（`apps/web/src/features/navigation.ts`）：

| 模块       | 内容                                                                                         | 问题                                                                                |
| ---------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 工作台     | 问候、快捷入口、我的项目列表、知识入口                                                       | 第一版后没有更新；不回答“今天做什么、项目怎么样、AI 做了什么”，是最该出彩却最弱的页 |
| 开发管理   | 开发概览、开发清单、开发排期                                                                 | 做得最深，但模块名就是“开发”，整个平台的业务只有这一块                              |
| 知识与资产 | 知识问答、知识库、代码资产、文档模板                                                         | **四项全是“规划中”**，给领导演示时点进去是空页，减分                                |
| 设置       | 个人 3 项 + 项目 8 项 + 企业 8 项 + 智能体 2 项 + 审计运维 4 项，共 25 项（其中 6 项规划中） | 过载；**计划与健康、团队与干系人、规模与商务是项目的业务内容，不是“设置”**          |

结论：

1. **骨架合理，分区不合理。** 图标栏 + 二级菜单 + 多标签页的外壳适合企业工具，不用推翻。问题在于模块按“我已经做了什么”来分，而不是按“实施项目要完成什么”来分。
2. **“项目”缺了一个家。** 项目计划、里程碑、团队、健康度是 PM 每周都看的东西，现在藏在设置里，导致平台看起来没有“项目”这个概念，只有开发清单。
3. **开发是“交付”的一个分支，不是全部。** 开发清单的四个阶段（FSD → 开发 → 顾问测试 → 用户测试）只覆盖 RICEFW 开发对象；配置、数据迁移、切换、培训都还没有位置。

### 1.2 权限

模型本身（权限点 → 单一角色 → 复合角色；企业级 / 项目级；模块范围与“只看本人”；`access` 模块统一校验）**是对的，可以直接承载扩展**，不需要重做。需要注意的是：

| 问题                                                                                             | 影响                                                   | 建议                                                                                                                         |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 权限码前缀 `delivery.*` 实际只指“开发清单”                                                       | 以后加配置清单、测试用例时，“delivery”这个词就被占用了 | 现在定好命名规则：新领域用各自前缀（`config.*`、`test.*`、`migration.*`），`delivery.*` 保留不改名，只改中文标签为“开发清单” |
| 业务顾问、测试人员、Basis 有角色但几乎没有功能可用（业务顾问只有 FSD，测试人员只有创建测试数据） | 除开发组外，其他人登录后没有理由每天用                 | 扩展领域时优先补这几类人的“主场”（第 3 节）                                                                                  |
| 缺少数据迁移、切换、培训等角色                                                                   | 目前无功能，不急                                       | 随领域上线再加，遵守“先登记权限点，再写 403/404 测试”                                                                        |
| 工作台没有自己的权限点                                                                           | 卡片若直接复用各页权限即可，不需要新权限点             | 规定：工作台每张卡片按其数据来源页的查看权限显示，没有权限的卡片不渲染                                                       |

### 1.3 其他

- **定位与诉求的张力要先讲清。** “加速整个实施项目”很容易滑向“做项目管理系统”（需求池、RAID、缺陷、变更、传输），而这些在定位决策里明确不做。本蓝图的解法是：**加速 = 帮我方顾问更快地产出交付物**，管理类事项仍以客户工具为准。这条线守住，方向就不会错。
- **护城河在资产沉淀。** 定位决策第 2 节指出提示词会过时，难复制的是评测用例、样本和团队经验。“知识与资产”因此不是装饰，而是长期价值所在，但应在交付物积累起来后再做（第 4 节第 3 期）。
- **视觉。** 现有 Plain 风格适合高密度的“干活”页面，但没有展示性。工作台与各概览页需要另一种表达（第 2.4 节），且不做一键换主题（理由见第 2.4 节）。

## 2. 工作台规划

### 2.1 定位

工作台是**登录后第一屏，也是给领导演示的封面**。它回答三个问题，按角色调整顺序：

1. **我今天要做什么？**（个人待办：我负责的阶段、等我回应的批注、待我测试的对象）
2. **项目现在怎么样？**（阶段与里程碑、进度、风险）
3. **AI 帮团队做了什么？**（助手产出与效率，这是平台区别于 Excel 台账的证据）

与开发概览的分工：工作台是**跨领域的摘要**，每张卡片只放一个结论加一个数字，点击后下钻到开发概览、开发清单或项目计划；开发概览仍是开发领域的深度驾驶舱。两者不重复。

### 2.2 版式（参照用户 2026-10-31 提供的 Uwang 等示意图）

便当格布局，桌面 12 栏，从上到下：

```
┌──────────────────────────────────────────────────────────────────────┐
│ 下午好，<姓名> · 10 月 31 日 星期五      [项目切换] [新建开发项] [问助手] │  页头：大标题 + 副标题 + 主操作
├──────────────┬───────────────────────────────┬───────────────────────┤
│ 项目阶段卡    │ 四张关键指标卡（2×2）            │ AI 洞察卡（深色）       │
│ 实现阶段      │ 开发完成率 72% ↑8%  │ 风险项 6 ↓2  │ “本周有 3 个 FSD 定稿   │
│ 距上线 46 天  │ 本周定稿 FSD 5      │ 冻结倒计时 12 天│ 后未派开发……”          │
│ ●●●●○○ 阶段条 │                     │              │ [查看并指派]           │
├──────────────┴───────────────────────────────┼───────────────────────┤
│ 交付趋势（大图：累积流 / 燃尽，近 8 周）          │ 我的待办（≤5 项，带进助手）│
├───────────────────────┬──────────────────────┼───────────────────────┤
│ 里程碑时间轴           │ 模块 × 阶段热力         │ 团队负载（本周）          │
├───────────────────────┴──────────────────────┴───────────────────────┤
│ 助手动态：最近的 FSD / 代码 / 测试数据产出，谁、哪个开发项、用时             │
└──────────────────────────────────────────────────────────────────────┘
```

视觉要点：一张主角卡用品牌色整块填充（建议放“项目阶段卡”或“AI 洞察卡”）；关键数字 32–40px；每张卡带趋势徽标（↑8%）；卡片 16px 圆角，三层底色（页面底 → 分区底 → 白卡）。

### 2.3 卡片清单与数据来源

| 卡片            | 内容                                             | 数据来源                                        | 现在能算吗                        |
| --------------- | ------------------------------------------------ | ----------------------------------------------- | --------------------------------- |
| 项目阶段        | 当前 Activate 阶段、阶段进度条、距上线天数       | 项目阶段与里程碑（`projects/options.mjs`）      | 能                                |
| 开发完成率      | 人天加权完成率与本周变化                         | 开发概览口径（development-overview.md 第 3 节） | 能                                |
| 风险项          | 逾期 / 冻结风险 / 计划缺口合计，与上周比较       | 开发概览 M01–M04                                | 能                                |
| 冻结倒计时      | 距开发冻结天数，冻结前预计做不完的项数           | 里程碑 `code_freeze` + M03                      | 能                                |
| 本周定稿        | FSD 与代码本周定稿数                             | `finalized_at`（开发概览 D3）                   | 能                                |
| 交付趋势        | 累积流或燃尽，近 8 周                            | 阶段状态流水回放（开发概览 10.2）               | 能                                |
| 我的待办        | 我负责、本周到期的阶段；等我回应的批注；待我测试 | 开发清单、批注                                  | 能                                |
| 模块 × 阶段热力 | 各模块各阶段件数与完成度                         | 开发概览 M05                                    | 能                                |
| 团队负载        | 本周每人计划人天，超载标红                       | 开发排期                                        | 能（需 `delivery.load:view`）     |
| 助手动态        | 最近 10 次助手产出                               | 助手运行日志、文档 / 代码版本                   | 能                                |
| **AI 洞察**     | 一段由模型生成的本周要点与建议动作               | 以上数据 + 模型                                 | 需新做（复用开发概览 WeekReport） |
| **AI 效能**     | 助手生成的 FSD 页数、代码行数、节省人天估算      | 运行日志 + 人天预估                             | 需定口径，见下                    |

“AI 效能”是给领导讲故事的核心，但必须可信：只做**项目和团队层面**的统计，不做个人排名（开发概览第 9 节的反指标）；“节省人天”须写明估算方法（例如：同类开发项历史平均人天 − 使用助手后的实际人天），没有基线前只展示产出量，不展示节省量。

### 2.4 视觉方向：分区共存，不做换主题

- **展示页**（工作台、开发概览、开发排期、计划与健康，以后各领域的概览）用便当格仪表盘语言：大数字、强调色主角卡、图表、三层底色。
- **干活页**（清单、详情、助手对话、设置）保留 Plain 骨架与密度，只吸收视觉语言：更大的圆角、品牌强调色、胶囊主按钮、柔和阴影。
- **不做一键换主题**：两种哲学的差异在布局、密度和组件结构，令牌换不了。2026-10-16 做过换肤、10-17 删除，就是这个原因。可以保留的切换只有浅色 / 深色。

这需要 DESIGN.md 升级为 3.0：解禁“卡片套卡片”（仅限仪表盘分区）、强调色填充、大字号数字，新增图表令牌（数据可视化色板）与仪表盘组件（指标卡、趋势徽标、洞察卡、图表卡）。

## 3. 目标信息架构

### 3.1 菜单

```
工作台        我的工作台（按角色）
项目          项目概况 · 计划与里程碑 · 团队与干系人 · 规模与商务        ← 从设置移出
交付          ┌ 开发：开发概览 · 开发清单 · 开发排期                     ← 现有
              ├ 测试：测试概览 · 测试用例 · 测试数据                     ← 第 2 期
              ├ 方案与配置：业务方案（BPD）· 配置清单                    ← 第 3 期
              └ 迁移与上线：数据迁移对象 · 切换计划 · 培训材料           ← 第 4 期
助手          全部助手入口：设计 · 开发 · 测试 · 方案 · 问项目
知识与资产    代码资产 · FSD 范例 · 文档模板 · 知识问答                  ← 有内容后再显示
设置          个人 · 项目配置（成员权限、SAP 系统、清单设置、模型）· 企业 · 智能体 · 审计运维
```

原则：

1. **按 Activate 交付物分领域**，每个领域固定三件套：概览（仪表盘）、台账（清单 + 详情）、助手。开发领域已经是这个形状，是其余领域的样板。
2. **项目是一级模块**，设置里只留真正的配置。
3. **规划中的页面不进菜单**。现在“规划中”的入口改为在工作台的“即将推出”卡片里预告，菜单里只出现能用的页面。
4. **助手有统一入口**，但工作仍从台账里的对象（开发项、测试用例）进入助手，保持“对象 → 助手 → 成果”的主线。

### 3.2 领域优先级

按“谁会每天用”和“与现有能力的距离”排序：

| 优先 | 领域       | 服务谁               | 为什么先做                                                                   | 边界提醒                                         |
| ---- | ---------- | -------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------ |
| 1    | 测试       | 业务顾问、测试人员   | 已有基础（测试数据创建、QAS 只读、开发清单的两个测试阶段）；让业务顾问有主场 | 测试用例与执行记录可以做；缺陷管理以客户工具为准 |
| 2    | 方案与配置 | 业务顾问、方案架构师 | Explore 阶段工作量最大；BPD、配置文档由助手产出价值明显                      | Fit-Gap 签核不做，只产出文档                     |
| 3    | 迁移与上线 | 数据迁移顾问、PM     | 迁移对象清单、映射规则、切换步骤都是标准交付物                               | 不连 PRD，不执行切换                             |
| 4    | 知识与资产 | 全员                 | 前面的定稿交付物积累后自动成为资产                                           | 跨项目沉淀规则按定位决策第 4 节                  |

## 5. 让人耳目一新的几个点

不是所有点都要做，这里列出效果与成本都合适的候选：

1. **AI 洞察卡**：工作台上一段模型写的“本周要点 + 建议动作”，每条可点击直接执行（指派、进助手）。开发概览已有周报能力，复用即可。
2. **问项目**：在命令面板里用自然语言问“FICO 模块冻结前还有几个没做完？”，回答附带可点击的清单。
3. **对象一条线**：一个开发对象从 FSD、代码、测试到上线的完整履历，在一页时间线上看完。
4. **交付物一键打包**：项目结束或里程碑时按模板导出全部定稿交付物（定位决策第 7 节已要求）。
5. **数字会动**：工作台指标的入场动画与趋势线描绘（遵守“不弹跳、不发光”，只做数值递增和线条描绘）。
