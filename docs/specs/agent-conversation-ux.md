# 智能助手对话体验设计指引（研究报告）

版本：0.2。日期：2026-10-16。第 7 节已由用户确认（全部按推荐方案）；P0、P1、P2 已实施，见第 8 节。适用范围：`apps/web/src/features/agent-workbench`，设计助手（`abap-fsd-agent`）与开发助手（`abap-dev-agent`）共用。

本文回答两个问题：

1. 运行过程（流式反馈、执行进度）应该怎么展示。
2. 右侧四个页签（开发项 / 文件 / 成果 / 对话）是否合理，应该怎么调整。

做法是先说明现状和实测数据，再整理 ChatGPT、Claude、Gemini 等成熟产品的做法和通用设计规律，最后给出我们的方案、分期和待确认事项。确认后，按第 6 节分期实施，每期单独提交。

## 0. 结论摘要

1. **不再显示“第 n 步 / 共 n 步”。** 现在的“步”其实是模型调用次数和工具调用次数，用户无法理解，总数也是事后才知道。用户应该看到的单位是“做了一件什么事”，例如“核对数据字典”。
2. **运行中只显示一行“现在在做什么 + 已用时”**，下面是按事情归并的活动记录。结束后折叠成一行摘要（如“已完成 · 用时 3 分 57 秒 · 核对 9 张表 · 编写 5 个章节”），可以展开，刷新后也还在。
3. **每条活动都写明对象**：表名、函数名、章节名。原始 JSON 只放在“原始结果”里。
4. **长时间没有输出时，要说明模型正在生成什么，并给出能感觉到的进度**（已生成字数、已用时），不能只靠转圈。
5. **一个错误只说一次，一个成功只提示一次。**
6. **右侧面板只放成果**（功能说明书 / 开发方案与代码）。对话切换移到对话区头部，对话编号写进地址栏；开发项信息和文件改为次要入口。

## 1. 现状与实测

### 1.1 机制

| 环节                                             | 现在的做法                                                                                                      | 用户看到的                                          |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 后端 `step` 事件（`agent-core/loop.mjs`）        | 每调用一次模型发一次                                                                                            | 状态文字“正在分析（第 n 步）…”，不说明在做什么      |
| `tool.start` / `tool.end`                        | 每次工具调用记一行；`tool.start` 带参数前 500 字，`tool.end` 带结果前 160 字                                    | “执行进度 · 15 / 17”，每行只有工具的中文名          |
| 工具标签（`session-model.mjs` 的 `TOOL_LABELS`） | 只看工具名，不看参数                                                                                            | 一连串“查询表内容或配置”，看不出查的是哪张表        |
| 结果摘要                                         | 工具返回文本的前 160 字                                                                                         | 展开后是 `{"status":"success","result":{"columns"…` |
| 推理流（`delta` 的 `reasoning`）                 | 只把状态改成“正在思考…”                                                                                         | 看不到在想什么                                      |
| 模型在生成工具参数（例如整章文档）               | `models/chat.mjs` 在流里已经拿到工具名，但不发事件                                                              | 几十秒到几分钟没有任何变化                          |
| 刷新后                                           | 最后一条消息用的是实时的 `run.steps`，加载时被清空（`ConversationTimeline.vue` 的 `progress` 插槽）             | 最近一轮的执行进度消失，更早的轮次还在              |
| 失败                                             | 正文写一条“本轮出错：…。已保存的进度不受影响…”，红框“本轮未完成”，底部提示条“本轮未完成，已保存的进度不受影响…” | 同一件事说三遍                                      |
| 成功保存                                         | 成果卡片里写一句“可在右侧‘成果’中阅读…”，底部灰条又写一句“已保存新版本。可在右侧‘成果’中阅读…”                  | 同一件事说两遍                                      |

| 14:04:59 | `edit_document`  | 原因“修复字段名错误，凭证类型描述在 TVAKT 的字段名为 BEZEI” | —      |
| 14:05:26 | `write_document` | 章节“附录 A 未决事项”“附录 B 生命周期分析”…                 | —      |
| 14:05:37 | `reply_comment`  | `comment_id` 为空，失败                                     | —      |

由此可以看出：

- **工具本身合计不到 3 秒，其余约 235 秒（约 99%）都在等模型**，两次调用之间隔 7～35 秒。写文档前的三段等待（33 秒、23 秒、35 秒）是模型在生成整章内容。用户感到“卡住”的正是这些时候，而这时界面没有任何新信息。
- **参数里本来就有用户关心的对象**：表名列表、SQL、函数名、章节名、修改原因。历史接口（`listToolCalls`）也返回了 `arguments`。所以“标题带对象名”这件事，前端就能做。
- 17 次调用其实只做了 5 件事：核对数据字典、查询配置、查找函数与权限对象、编写文档、修订文档。
- 最后一次 `reply_comment` 失败，是模型自己用错了工具（这一轮并没有批注），却以失败步骤展示给用户，容易让人误以为出了问题。

全库统计：设计助手共 32 轮，平均每轮 9 次工具调用，最多一轮 43 次。调用最多的是 `runQuery`（113 次）和 `ddicElement`（78 次），正好是用户反映“看不出在查什么”的两类。

## 2. 成熟产品怎么做

说明：OpenAI、Anthropic、Google 都很少在文档里描述界面细节（OpenAI 的帮助页这次也拒绝了抓取）。下面标“来源”的有公开资料可查；标“观察”的来自对产品的直接使用，截至 2026 年年中，界面会继续变化。

### 2.1 ChatGPT

- **推理过程**：运行中只显示一行在变化的状态文字，结束后收成“Thought for N 秒”的折叠条，点开能看推理摘要和工具调用。（来源：AI UX Playground 的 Progress Steps 模式）
- **Deep Research**：先把研究计划作为普通消息发出，用户认可或修改后才开始；过程中步骤显示在一个实时更新、可展开的面板里，结束后收成对话里的一个小组件；报告以卡片形式出现在回答中。不足是长报告在聊天流里不好读，也没有专门的文档阅读器。（来源：Deep Research UI 对比文章）
- **Agent 模式**（观察）：边做边用一句话说明正在做什么；用户可以随时打断或接管；发邮件、付款等有后果的操作前会先确认；任务较长时，用户可以离开，完成后再收到通知。

### 2.2 Claude

- **扩展思考**：回答上方一个可折叠的思考块，默认收起。（来源：AI UX Playground）
- **工具调用**（观察）：工具调用以紧凑的单行插在文字之间，例如“已搜索网页”加结果数，点开能看查询词和来源。模型在调工具前常先写一句要做什么，这句话本身就是进度说明。
- **Artifacts**：成果在对话右侧的分栏中打开，可以切换版本。（来源：Artifacts 与 Canvas 对比文章）对话列表在左侧栏，每个对话有独立地址。（观察）
- **Claude Code 的教训**：新版本把连续读文件合并成“Read 5 files”，用户随即抱怨看不到读了哪些文件，要求合并行至少写成“工具：主要对象”（文件路径、搜索词）。（来源：Claude Code 议题 21359、21151）**结论：可以合并，但不能丢掉对象名。**

### 2.3 Gemini

- **Deep Research**：计划以专门的卡片展示，可以编辑、合并、拆分、调整顺序，点“开始研究”后执行；运行中状态显示“正在研究…”，可点“显示思路”跟看推理过程；可以离开，完成后收到通知。（来源：Gemini Deep Research 使用指南、Google 帮助中心）
- **布局**：过程放在单独的“思路”面板，和对话分开；报告也放在副面板。不足是步骤藏在报告下方，回看要翻很久。（来源：Deep Research UI 对比文章）
- **Canvas**：成果在侧边面板中编辑，可以导出到 Docs。（来源：Artifacts 与 Canvas 对比文章）

### 2.4 其他参考

- **Perplexity**：可折叠的“Steps”轨迹，列出搜索词和访问过的来源。（来源：AI UX Playground）
- **Cursor Agent**：工具调用和文件读取以可展开的时间线展示。（来源：AI UX Playground）
- **ai-elements**（我们已引入其 Vue 版）：`Chain of Thought` 组件默认收起，每步有图标、标签、描述和 complete / active / pending 状态，可以附带搜索结果标签；`Tool` 组件头部是工具名加状态徽标，输入和输出可折叠。（来源：ai-elements 文档）

### 2.5 通用设计依据

- **10 秒原则**：超过约 10 秒的等待，用户注意力会离开，系统应告诉用户大约何时完成；可以的话用完成比例，而不是只放动画。（来源：Nielsen Norman Group）
- **过程轨迹的反模式**（来源：AI UX Playground）：
  - 默认展开全部过程，把答案埋在下面。
  - 步骤没有时间或耗时，看不出慢在哪里。
  - 使用“处理中”这类不说明任何事情的标签。
  - 结束后轨迹消失，无法回看。
- **流式过程提示**：显示工具的开始和结束，区分进行中和已完成；不要把用户看不懂的内部细节或频繁闪动的更新推给用户。（来源：inference.sh Agent UX 模式）

## 3. 共同规律

| #   | 规律                                       | 对我们的含义                                               |
| --- | ------------------------------------------ | ---------------------------------------------------------- |
| 1   | 用户看的是“在做什么事”，不是计数           | 去掉“第 n 步 / 共 n 步”                                    |
| 2   | 运行中只有一行最显眼的状态，并持续变化     | 状态行固定在当前回复顶部，写清动作和对象，配一个走动的计时 |
| 3   | 过程默认收起，答案和成果是主角             | 结束后折叠成一行摘要；运行中只展开当前活动                 |
| 4   | 合并同类，但保留对象名                     | 同一阶段的查阅合成一行，后面列出表名；编写按章节列出       |
| 5   | 细节按需查看，用人能读的形式               | SQL 用代码块，查询结果用小表格，原始 JSON 放到最后一层     |
| 6   | 长任务要说明“还在进行、大概多久、可以离开” | 显示已生成字数和已用时；超过 1 分钟提示可以离开页面        |
| 7   | 需要用户决定的事单独突出                   | 提问卡片保持现状；状态行同时写“等待你的确认”               |
| 8   | 过程可回看                                 | 刷新、切换对话后仍能展开每一轮的活动记录                   |
| 9   | 成果放在侧边分栏，对话列表不和成果抢位置   | 见第 5 节                                                  |

## 4. 运行过程的设计方案

### 4.1 三层结构

运行中（示意）：

```text
设计助手 · Gemini 3.1 Pro
◌ 正在编写「3 业务逻辑」… 已生成约 2,400 字 · 共 2 分 58 秒
  ✓ 查阅 SAP 系统  表 VBAK、VBAP、TVKO、T001、KNA1、MAKT 等 9 张 · 函数 CONVERT_TO_LOCAL_CURRENCY · 权限对象 V_VBAK_VKO   11 次
  ✓ 编写文档       1 开发需求部分、2 功能规范
  ✓ 查阅 SAP 系统  表 TVAKT   1 次
  ◌ 编写文档       3 业务逻辑
```

结束后（默认收起，点开即上面的列表）：

```text
▸ 已完成 · 用时 3 分 57 秒 · 核对 9 张表 · 查询 4 次 · 编写 5 个章节 · 修订 1 处
```

- **第一层：状态行**。只在运行中显示，写清当前动作和对象，加总用时（每秒更新）。正文开始流式输出后，状态行隐藏，正文本身就是反馈。
- **第二层：活动记录**。按 4.2 归并，每行包括类别、对象、次数，结束后的行显示耗时。运行中只展开当前活动，结束后整体收起成一行摘要。
- **第三层：调用详情**。点开某一行后，逐条列出调用：输入用人能读的形式，输出用摘要或小表格，最后才是“原始结果”。

### 4.2 活动类别与对象提取

| 类别               | 工具                                                                                 | 行内对象（从参数提取）                         | 详情                                  |
| ------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------- | ------------------------------------- |
| 核对数据字典       | `ddicElement`、`ddicRepositoryAccess`、`objectStructure`                             | `path` 中的表 / 结构名，去重                   | 每张表的字段数；原始结果              |
| 查询系统数据与配置 | `runQuery`、`tableContents`                                                          | SQL 中 `FROM` 后的表名，必要时加条件中的关键值 | SQL 代码块；结果前 5 行的小表格；行数 |
| 查找程序与函数     | `searchObject`、`findObjectPath`、`findDefinition`、`usageReferences`、`objectTypes` | `query` 与对象类型                             | 命中的对象列表                        |
| 阅读源码与文档     | `getObjectSource`、`classComponents`、`abapDocumentation`                            | 对象名                                         | 行数；原始结果                        |
| 阅读资料           | `list_materials`、`read_material`、`read_document`、`read_artifact`                  | 资料名、章节名                                 | —                                     |
| 编写成果           | `write_document`、`write_artifact`、`import_code`、`sync_from_sap`                   | `changes[].section`（章节名）                  | 每章的变更说明（`changes[].summary`） |
| 修订成果           | `edit_document`、`edit_artifact`                                                     | `reason`                                       | 修改前后片段                          |
| 校验               | `check_document`、`check_code`                                                       | —                                              | 校验发现的问题数与列表                |
| 等待你的确认       | `ask_user`                                                                           | 问题数                                         | 由提问卡片承担                        |
| 回复批注           | `reply_comment`                                                                      | 批注摘要                                       | 回复内容                              |

规则：

- **按阶段归并**：前五类都是只读查阅。两次写入或修订之间的所有查阅，合成一行“查阅 SAP 系统”（只涉及资料时写“阅读资料”），行内按“表 / 函数 / 权限对象 / 程序”分组列出对象，详情里再按上表的类别分开。编写、修订、校验、确认、回复批注各成一行。这样保留了“先查、再写、再查”的先后顺序，又不会因为模型交替使用不同的查询工具而拆成很多行。
- 实测中，按“连续同类”合并时，1.2 节那一轮会拆成 14 行，因为模型在查表、查配置、查函数之间来回切换；按阶段归并只有 6 行（查阅 → 编写 → 查阅 → 编写 → 修订 → 编写），最后那次内部失败的回复批注只在详情里记录。
- 行内对象去重，每组最多列 6 个，多出的写“等 n 张”。
- 编写和修订按章节列出，因为这是用户最关心的进度。
- **失败的处理**：业务上有意义的失败（例如 SAP 查询报错）在行尾用琥珀色写“1 次未成功”，详情里给原因；模型自己用错工具、或被重复调用拦截之类的内部失败，只在详情里用灰字记录，不标红。
- 未登记的新工具，按工具名进入“其他操作”，不出现英文名。

这些规则是纯函数，放在 `session-model.mjs` / `presentation.mjs`，在 `tests/unit/web` 补测试；实时流和历史回看共用同一套。

### 4.3 状态行的文字

| 收到的事件                     | 状态行                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------- |
| 轮次开始，还没有任何事件       | 正在理解需求…                                                                      |
| `step`（新一次模型调用）       | 正在思考下一步…（**不再显示步数**）                                                |
| `delta` reasoning              | 正在思考…；如果推理摘要里有小标题（Gemini 常以加粗短句开头），显示最新的小标题     |
| `tool.prepare`（新增，见 4.4） | 正在编写「3 业务逻辑」… 已生成约 2,400 字                                          |
| `tool.start`                   | 正在核对 VBAK、VBAP 等表结构… / 正在查询 TVKO…                                     |
| `delta` text                   | 隐藏状态行（正文在流式输出）                                                       |
| `step` 带 `retry`              | 模型服务繁忙，n 秒后第 k 次重试…                                                   |
| 提问卡片出现                   | 等待你的确认                                                                       |
| 同一状态超过 60 秒             | 追加一行灰字：“模型仍在生成，较长的章节通常需要 1～3 分钟。离开页面不会中断运行。” |

总用时在整行末尾一直走动，确保界面始终在变化（10 秒原则）。不提供完成百分比，因为模型何时结束无法预知，假的进度条比没有更糟。

### 4.4 需要后端配合的两点

1. **`tool.prepare` 事件**：`models/chat.mjs` 在流中一拿到工具名就通知循环；循环发 `tool.prepare`（`id`、`name`），之后每增加约 500 字参数，发一次累计字数。参数还没写完，章节名可能拿不到，所以先显示“正在编写文档… 已生成约 n 字”；能从已到达的参数里解析出 `section` 时再补上章节名。这一点直接解决“写文档时几分钟没动静”。事件类型要加进 `packages/contracts/agent-core` 的 `sse` 定义。
2. **结构化的结果预览**：`tool.end` 现在只带 160 字文本，无法画成表格。建议 SAP 工具的结果在 agent-core 里额外生成一个小的 `preview`（列名、前 5 行、总行数；DDIC 为字段数），随 `tool.end` 发出，也随工具调用记录保存。这部分不影响模型看到的内容。

### 4.5 错误与结束提示

- **失败**：只保留红框（标题“本轮未完成”、原因一句、操作“重新发送”、可展开的诊断详情）。正文里的“本轮出错：…”只给模型的历史投影使用，界面不再显示；底部提示条在失败时不显示。顺带修掉“。。”。
- **成功并保存了新版本**：成果卡片是唯一提示，底部灰条不再重复。
- **停止**：保留一句“已停止本轮运行。可补充需求后重新发送。”
- **等待回答**：提问卡片自身已经说明，底部提示条不再重复。

### 4.6 回看

刷新或切换对话后，最后一轮也要用已保存的工具调用生成活动记录（修复 1.1 中的问题）。运行编号、复制编号这类诊断信息收进摘要行展开后的底部，不放在每条回复的头部。

## 5. 右侧面板

### 5.1 现状分析

| 页签   | 内容性质                                 | 作用范围 | 使用频率           | 问题                                                                    |
| ------ | ---------------------------------------- | -------- | ------------------ | ----------------------------------------------------------------------- |
| 开发项 | 静态信息（模块、类型、业务功能点、模型） | 开发项   | 低，偶尔查看       | 与成果平级，占了主要位置；“模型”已在输入框显示，重复                    |
| 文件   | 本次对话上传的附件及提取预览             | 对话     | 低，上传后偶尔核对 | 与输入框附件区重复；作用范围与相邻页签不同，容易误解                    |
| 成果   | 功能说明书 / 开发方案与代码              | 对话     | 高，核心           | 只是四个页签之一；开发助手里还有一层“代码 / 开发方案 / 差异 / 依据”页签 |
| 对话   | 本开发项的对话列表                       | 开发项   | 中，切换时用       | 导航功能放在内容面板里；打开列表就看不到成果，二者互斥                  |

“怪”的根本原因：**四个页签性质各不相同**，有导航（对话）、有背景信息（开发项、文件）、有工作成果（成果），作用范围也不一致（开发项级和对话级混排），却被做成平级的互斥页签。参照的产品里，成果在右侧分栏，对话列表在左侧或头部，项目资料在项目页，三者从不放在同一组页签里。

### 5.2 建议

- **右侧面板只放成果。** 头部按钮改为“成果”（显示当前版本），有成果的对话在宽屏下默认打开，并记住用户上次是开还是关。开发助手保留“代码 / 开发方案”两个视图；“差异”和“依据”改为工具栏上的“与上一版比较”“查看依据”，不再与文档平级。
- **对话切换放到对话区头部。** 现在的标题“销售订单基本清单 · 设计助手”改为当前对话标题加下拉箭头，下拉列表显示对话标题、时间、成果版本，旁边是“新对话”按钮。地址栏带上对话编号（如 `?session=<id>`），刷新和分享都能定位；`localStorage` 只在地址里没有编号时兜底。对话支持改名，以解决标题重复。
- **开发项信息改为头部弹出卡片。** 点击头部的“00006 · 销售订单基本清单”弹出模块、类型、业务功能点、开发对象、事务码；去掉“模型”一项。
- **文件就近显示。** 附件在发送它的那条消息上显示文件标签，点击后在右侧面板临时显示提取预览（带“返回成果”）；对话头部显示“资料 n”入口，可查看本对话的全部文件。

备选方案：如果希望改动小一些，右侧保留两个页签“成果 | 资料”（资料 = 开发项信息 + 文件），对话切换照样移到头部。

## 7. 待确认事项（2026-10-16 用户确认：全部按推荐方案，P0 与 P1 一起做）

1. **归并粒度**：按阶段归并（两次写入之间的查阅合成一行，推荐，见 4.2），还是整轮所有查阅合成一行（更短，但看不出“写完又回头核对”）。
2. **是否显示模型的推理内容**：只在状态行显示推理小标题（推荐），还是在活动记录里提供可展开的完整推理摘要。不同模型的推理文本质量差别大，可能有英文或冗长内容。
3. **右侧面板**：5.2 的主方案（只放成果），还是备选（成果 | 资料）。
4. **对话切换器的位置**：对话区头部下拉（推荐），还是对话区左侧的可收起列表（更像 ChatGPT / Claude，但会挤占对话宽度，本页已有左侧导航栏）。
5. **实施顺序**：先做 P0（纯前端，见效最快），还是 P0 与 P1 一起做（“写文档几分钟没动静”的根本解决依赖 P1）。

## 8. 实施记录

### 8.1 P0 + P1（2026-10-16）

- **后端**：`models/chat.mjs` 在流中拿到工具名与参数增量时回调；`agent-core/loop.mjs` 发 `tool.prepare`（工具名、已生成字符数、已能解析出的章节名，每增加 400 字符最多发一次）；`tool.start` 改为发送解析后、去掉正文的参数；工具结果由 `agent-core/preview.mjs` 生成预览（表格、对象列表、可读错误、文字），随 `tool.end` 发出，并存入新增列 `preview`（迁移 `1792300000000_agent-tool-preview`，设计与开发助手的 `tool_call` 表各一列）。失败说明不再出现“。。”。

### 8.2 P2（2026-10-16）

- **选中即批注改为浮动按钮**（用户 2026-10-16 提出，参考 Claude 的“回复”）：在 FSD、开发方案或代码中选中文字，选区上方出现一个小的“批注”按钮；点击后才在原位置弹出批注框（引用原文、输入框、Ctrl + Enter 提交）。按钮和批注框都浮在页面之上，不插入页面，不再引起跳动；选区取消、滚动或点击别处时按钮消失，批注框只在 Esc、取消或点击外部且未填写时关闭。共用组件 `agent-workbench/SelectionComment.vue`。
- **右侧面板只放成果**：头部按钮改为“成果”，有成果的对话在宽屏下默认打开，并记住读者上次关闭；开发助手只保留“代码 / 开发方案”两个视图，“与上一版比较”“查看依据”改为工具按钮。
- **对话切换**：对话区标题即当前对话名称，点开下拉切换、新建或改名（`PATCH …/sessions/:sessionId`，两个助手各一个，名称 1～200 字）；地址栏带 `?session=<id>`，刷新和分享能定位，读者主动切换会记入浏览历史（后退回到上一个对话）；`localStorage` 只在地址里没有编号时兜底。
- **开发项信息**改为点击头部标题弹出的卡片，去掉“模型”（输入框已显示）。
- **文件**：对话区头部显示“资料 n”，点开列出本对话的文件，点击后在右侧面板预览提取内容，可“返回成果”。附件目前不记录属于哪条消息，所以没有放在消息上；如需要，要在后端记录附件与消息的关联。

### 8.3 用户试用后的调整（2026-10-16）

- 对话区标题去掉，当前对话（可切换、改名）、“资料 n”“新对话”并入页面头部。
- 运行中的活动行不再自动展开；查询在 0.8 秒内结束时状态行不报名字，避免查表时闪烁。
- 只提问的轮次不再渲染空的正文和操作区，摘要行与提问卡片紧挨。
- “功能说明书已保存”卡片改为一行高亮链接（“功能说明书 · 第 n 版已保存 打开”）。
- 成果面板外层不再滚动，文档阅读区占满剩余高度，只保留一个滚动条；“本版改动章节”收成可展开的“本版改动 n 个章节”。
- 输入框底栏统一为 12px；SAP 系统选择只显示 DEV / QAS，完整系统名在悬停提示中；空间不足时先隐藏“Enter 发送”提示。
- 修复：首条消息写入 `?session=` 时整页被重建、发送的那一轮不显示（布局按完整地址重建页面，两个助手的路由改为只按路径）。

### 8.4 已知限制

- **当前默认模型拿不到“已生成字数”的连续进度**。用同一个服务（ofox.ai 转发 Gemini 3.1 Pro）单独测试写一章约 7,400 字符的工具调用：前 90 秒没有任何数据（没有推理流，也没有正文），随后参数在约 45 秒内分 3 块到达。所以这类等待只能靠状态行的计时和“模型仍在生成…”说明；参数边生成边推送的模型（OpenAI、DeepSeek、Claude 等）能显示连续增长的字数。要进一步改善，需要换服务商或让模型分更小的段落写，不属于界面范围。
- 旧轮次没有保存预览（`preview` 为空），展开后只有“原始结果”。
- 模型在没有批注时也会调用 `reply_comment`（本轮与 `2c99544f` 都出现），界面已把这类内部失败收进详情；提示词是否需要调整另行决定。
