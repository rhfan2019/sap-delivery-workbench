# FSD 批量测试改造说明

## 交付结构

新增工具集中在 `tools/fsd-batch/`，由命令行执行器、共享日志模块和离线分析器组成。没有新增独立 Web 服务。HTML 报告可直接打开，现有前端运行日志页同步展示公共统计。

| 模块 | 入口或文件 | 职责 |
|---|---|---|
| 执行器 | `fsd-batch.cmd` / `cli.mjs`、`lib/runner.mjs` | 顺序复制、调用原接口、回答预置问题、恢复、回读成果 |
| 复制接口 | `lib/clone-route.mjs`、`lib/policy.mjs` | 鉴权、基本字段白名单、请求幂等、项目锁 |
| 结构化日志 | `lib/recorder.mjs` | 每轮独立 JSONL、时间戳、序号、请求与输出、凭据字段脱敏 |
| 分析器 | `lib/analyzer.mjs`、`lib/report.mjs` | 分步耗时、模型与提供方调用、失败原因、JSON/Markdown/HTML |
| 批次状态 | `lib/storage.mjs` | 原子检查点、执行进程锁 |
| 测试配置 | `configs/acceptance.json` | DEV-0007、DEV-0002 的独立测试假设与预置回答 |

## 与前端执行一致

执行器使用与页面相同的开发项工作区接口，包括默认模型查询、创建运行、SSE 事件、回答业务问题、工作流初稿确认和最终成果读取。模型生成、提示词、结构及引用校验、SAP 对象只读核验、质量审查、保存仍由既有公共后端实现。执行器不直接调用模型，也不另写说明书生成流程。

初稿自动确认通过标准工作流接口完成，记录 `testOnly: true`。终点为完整版本保存并进入 `final_review`；不自动完成顾问最终签认，不执行 SAP 采购审批、转单或其他业务写入。

## 隔离与断点续跑

1. 每个源开发项只创建一个基本信息副本，编号采用批次的上海时间前缀。附件、历史说明书、历史回答、历史会话、审批与备注不复制。
2. 每项单独的副本、会话、预置答案集合及日志目录。首次运行空消息历史；不传递上一开发项会话或交接上下文。
3. 同批次串行执行。若旧调用可能仍在运行，停止批次，不启动下一开发项。
4. 复制和生成均在调用前持久化请求 ID；响应丢失先查回执。恢复不会无条件创建新副本或新调用。
5. 已保存的完整成果自动跳过。失败项只有显式 `--retry-failed` 才重试；缺少或歧义答案暂停该项，补充配置后恢复。
6. 流式生成中断只能恢复到已持久化运行/版本边界，不能从任意模型 token 接续。

## 公共程序改造

- `delivery/items.mjs`：注册复用项目权限体系的基本信息复制接口。
- `abap-fsd-agent/routes.mjs`：共享日志接入、鉴权轨迹查询、按请求 ID 查回执、诊断统计。
- `runs.mjs`、`generation.mjs`：记录模型调用与提供方各次尝试，包括截断续写的真实请求及输出；日志写入失败明确终止，不留下挂起运行。
- `executor.mjs`：本地校验计时、SAP 轨迹传递；失败终态一次保存完整步骤与错误，修复原先状态已失败但步骤仍运行的问题。
- `object-verification.mjs`：SAP 只读工具的耗时、结果和失败记录。
- `specification.mjs`：模型输出契约排除可信人工确认状态，存储契约不变；确认错误附带字段路径。
- `errors.mjs`、`models/transport.mjs`：日志写入失败和域名配置错误的独立分类；校验失败给出可执行恢复说明。
- 前端 `RunDiagnosticsView.vue`、`useAssistantRun.ts` 与步骤类型：展示公共耗时、token、错误位置，并显示运行时动态添加的设计规划步骤。

现有文件原件保存在本目录 `backups/`。工作区不属于 Git 仓库，因此没有提交或分支操作。环境备份含凭据，不能公开分享。

## 日志统计口径

运行完成、结构校验通过、版本已保存、最终完整成果保存、业务质量分别统计。业务质量保持“未评估”；结构通过不能替代业务验收。自动质量审查及待核实事项另行保留。

步骤耗时包含内部模型调用，不重复累加。每次模型调用与提供方尝试独立计数；输入/输出 token 在尝试之间求和，推理 token 是输出 token 的子集，不额外叠加。缺失数据标记未知；只开始未结束的调用标记中断，损坏日志明确报出。旧版本日志无法补造新版才开始采集的细节。

请求、候选输出、错误、重试与最终说明书保留在本地；不采集模型私有思维链，仅记录提供方给出的推理用量。访问 API 日志需要原有运行权限，本地文件应按项目资料管理。

## 原始 16 分钟失败的证据

原运行 `31b220e5-0ed4-4486-a6bd-ebfa37ced5bf` 的数据库快照显示：

| 阶段 | 耗时 |
|---|---:|
| 澄清检查 | 35.112 秒 |
| 设计任务规划 | 113.398 秒 |
| 结构化草稿生成 | 577.410 秒 |
| 自动修正的模型调用 | 236.130 秒 |
| 总运行 | 962.135 秒（16 分 2 秒） |

两次校验都记录 `untrusted_confirmation` 两处。初稿输出 29,033 token（其中推理 16,726），修正输出 13,476 token（其中推理 1,170）；完整重写扩大了等待。原模型为 DeepSeek-V4-Pro，本次按当前默认配置使用 Qwen3.8-Max，不能将不同模型与不同输入下的时间当作严格性能对照。

没有证据表明本地 JSON Schema 校验消耗了这些分钟。Schema 规模可能增加生成负担，但需要同模型、同输入、多次对照才能量化。当前优先修复生成契约与可信状态冲突、终态日志缺失，并明确区分本地校验和模型修正。原始证据位于 `runs/original-run-analysis.json`。

## 优化方向

1. 根据阶段耗时和 token 先定位模型长推理、长正文及整份重写；不要直接删减校验以换取表面成功。
2. 可信人工状态由服务端维护；输出契约与校验器一致，减少可避免的自动修正。
3. 后续可对字段级补丁修复、按设计任务分段生成做同用例对照。分段要保持统一引用、全局一致性和最终完整校验。
4. 维持明确失败说明与恢复入口；同类失败保留运行编号，避免用户盲目多次重跑。
5. 日志目录需持久化。多实例使用共享持久卷或集中日志存储；当前文件记录器不提供跨机器汇聚。

实际验收结果与每轮详细记录见验收批次报告；最终交付报告会区分已验证结果和剩余限制。
