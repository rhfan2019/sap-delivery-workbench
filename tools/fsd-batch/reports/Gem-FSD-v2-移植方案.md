# Gem FSD v2 移植方案

日期：2026-10-06  
状态：待审阅的设计方案；本次仅编写方案，不实施、不启动模型测试。  
目标：移植成熟 Gem 中“需求到 FSD”的能力，保留现有逻辑，通过独立 v2 验证交付质量、耗时和可维护性。

## 1. 已确认范围与设计建议

已确认：

- Gem 原指令覆盖需求、FSD、技术分析和代码生成；此次只移植需求到 FSD。
- 优先采用成熟 Gem 的业务分析方法，不继续围绕旧版复杂 JSON 链路叠加优化。
- 保留现有逻辑，新增独立 v2。
- 保持此前的运行隔离要求，前端与测试执行器调用同一执行程序。
- 本次只出具方案。

本方案建议：

- 以 Gem 的阶段一九章为 FSD 主体；阶段二中确实属于功能规格的内容，仅选择性合并到相应章节，不启动第二个技术设计阶段。
- 完整 FSD 正文优先采用 Markdown；存储、版本、来源与可信状态由程序管理。
- 单次生成包含必要的业务分析、简短计划和自查；不默认增加独立规划、全文证据修订或第二次模型审查。
- 第一阶段继续使用当前默认 LLM，先验证流程和提示词的改进；五分钟作为目标，不作为未经验证的承诺。

## 2. 方案选择

| 方案 | 优点 | 主要问题 | 建议 |
|---|---|---|---|
| 仅替换旧版提示词 | 表面改动小 | 仍执行强制规划、完整 JSON、自动全文修订；与 Gem 输出方式冲突 | 不采用 |
| 新增独立 Gem FSD v2，共用基础服务 | 能保留旧版，独立验证；不会继承旧执行链成本 | 需新增 Markdown 成果存储与适配界面 | 推荐 |
| 用 v2 全面替换旧版 | 长期只维护一套逻辑 | 尚未证明质量和速度，历史数据及接口迁移风险大 | 本次不做 |

这里的“保留旧版”是保留现有可运行实现、历史成果和默认入口。当前已有的日志及诊断改造也保留，不在此次移植中回退或重构它们。

## 3. Gem 内容移植清单

| 原 Gem 内容 | v2 处理 | 说明 |
|---|---|---|
| SAP 业务顾问角色、需求理解、信息缺失处理 | 保留并适配 | 明确用户需求、测试假设、系统事实与未知项 |
| 阶段一九章业务分析 | 作为 FSD 主体保留 | 保留成熟内容组织，不先改造成旧版四章或全量 JSON |
| 最低业务颗粒度、变体、异常、标准对标 | 保留 | 不以提速为理由删除必要业务分析 |
| 选择条件、输出、关联、计算、权限与测试 | 保留并校对完整性 | 第五章明确加入输出字段、显示/导出/下钻设计；权限内容只写有依据的对象或待核实项 |
| 第八章魔鬼代言人 | 保留自查方法，调整固定数量要求 | 只报告具体相关缺陷，不强求“至少两个致命漏洞” |
| 即时证据 | 改为简短“本章检查结论与依据” | 引用已提供的需求/决定/字典资料；不能把自述数量当成真实系统核验证据 |
| DDIC 依赖清单与字典注入 | 保留，输入来源适配平台 | 可用资料先注入；缺失列依赖，不编造字段或 API 签名 |
| 阶段二中的必要技术可行性、数据路径 | 选择性并入第五/九章 | 仅保留会影响 FSD 实现成立的内容，未知则明确标注 |
| 独立阶段二 TSD、开发任务分解 | 不移植 | 不在此次 FSD 范围内 |
| 阶段三 ABAP 代码、类框架、命名与 SQL 编码规则 | 不移植 | 不加载相应提示词，也不输出代码 |
| YCL_FRH_REPORT 附件缺失全局阻断 | 删除 FSD 阶段的这项依赖 | 不让代码框架附件阻塞业务说明书 |
| 阶段解锁与确认 | 交给程序管理 | 文本“确认”不能替代对具体版本的人工确认记录 |
| 修改即完整重写 | 首轮不要求模型重复整篇 | 改动时可替换完整受影响章节，由程序组装完整文档；初期不做复杂字段级补丁 |
| 强制公开完整思考过程 | 不移植 | 只输出业务依据、检查结论、风险与待确认事项 |
| S/4HANA 静默升级 | 改为依据实际平台提出方案 | 不擅自改写用户的 ECC/S/4HANA 等环境约束 |

九章交付：业务需求概览与假设；生命周期/变体/状态；业务对象与数据来源；标准功能对标；报表方案；适用的多步骤自动化；测试基准；业务自查；DDIC 依赖与待核实事项。第一阶段覆盖目前两个 R 类案例；I/C/E 不静默套用报表模板，后续另行扩展。

## 4. v2 执行流程

```text
选择 Gem FSD v2 → 建立独立会话
    ↓
程序准备需求、有效回答、附件、平台信息和可用字典
    ↓
一次模型调用
    ├─ 有必须回答的业务问题：输出问题 → 等待回答
    └─ 信息足够：输出完整九章 FSD，包含自查
              ↓
       本地文档结构检查
              ↓
       保存独立候选版本并回读
              ↓
       顾问审阅 / 修改意见 / 确认该版本
```

### 4.1 不再默认执行的步骤

- 独立的模型需求预检调用。
- 独立的设计任务规划调用。
- 旧版全量 FSD JSON 生成及 AJV 规格合同。
- 生成完成后无条件再做一次全文证据修订。
- 首次交付后自动进入“正式版”再次全文生成。
- 为了取得表面成功而连续自动重试。

这不是取消需求理解和自查，而是让它们服务于同一次 FSD 交付。独立模型审查若以后确有收益，可作为明确触发的功能另加，不进入首轮基线。

### 4.2 澄清与字典缺失

同一次调用只能返回一种结果：完整 Markdown 文档，或者轻量的澄清问题对象。澄清对象只包含问题标识、问题、影响、选项及是否允许自由回答，不携带整份规格。

仅当不同答案会改变范围、计算、粒度、不可逆动作或关键验收结论时阻塞。已有回答不重复提问；低影响选择可作为明确假设继续。缺少某个技术字段不一律阻塞，列为候选和依赖；若直接影响核心可行性，则明确提出阻塞项。

候选保存、存在关键待确认项、顾问已接受分别记录。保存成功不等于业务质量通过，也不等于可以直接实施。

### 4.3 核验策略

首轮以已经准备的字典/证据为输入，不自动触发多轮 SAP 查询与全文重写。在线核验作为独立、显式动作：只查询与缺口相关的只读元数据，将结果转为精简事实包；如需修改，只更新受影响章节。

原始工具结果和凭据处理沿用平台安全边界。证据的真实来源、时间、系统身份和验证状态由服务端记录，不让模型填写可信状态。

## 5. 版本隔离与复用边界

现有提示词路径包含 `v1`，但 manifest 中的版本已是 `2.0.0`。新旧引擎不能仅靠这个数字区分。建议显式引擎标识：旧引擎 `fsd-legacy`，新引擎 `gem-fsd-v2`；提示词版本另记。

| 能力 | 处理方式 |
|---|---|
| 登录、组织/项目/开发项权限 | 复用既有服务与校验规则 |
| 默认模型配置、凭据、网络允许列表、流式传输 | 复用基础接入，不复制模型调用代码 |
| 附件读取与解析、项目系统画像 | 复用服务；v2 单独构造输入 |
| 结构化日志记录器 | 复用，新增引擎及提示词版本字段；保留调用、耗时、用量、失败信息 |
| 旧版规划、生成、证据修订执行器 | 不复用，不在其中大量追加 v2 条件分支 |
| 旧版全量 Schema、渲染和保存函数 | 不复用为 v2 成果合同 |
| 会话、运行与成果版本 | v2 独立命名空间与记录；建议采用新增 v2 表，保留旧表约束与语义 |
| Markdown 阅读、附件展示、问题交互 | 在接口兼容的范围内复用纯展示组件；不直接复用旧 spec 编辑器 |

现有 `saveRevision()` 会修改 spec 身份、从 spec 渲染 Markdown、以 spec 计算哈希，并推动旧工作流。因此 v2 需要自己的成果仓储与工作流适配，不能把 Markdown 塞进旧 spec 字段冒充兼容。

建议新增目录（均为拟议结构，本次不创建程序）：

```text
packages/agents/gem-fsd/v2/             提示词、来源说明、版本清单
packages/contracts/gem-fsd-v2/         轻量交互与成果元数据合同
apps/api/src/gem-fsd-v2/               上下文、执行、文档检查、保存、路由
apps/web/src/features/gem-fsd-v2/      v2 独立入口和成果审阅
tools/fsd-batch/adapters/gem-fsd-v2/   测试执行器接口适配
```

数据库变化仅新增 v2 所需记录，不改写旧 revision 内容。新表同样需要组织/项目隔离、鉴权、请求幂等、并发版本控制及索引，不因独立目录降低权限要求。

## 6. 输出、保存与校验

### 6.1 文档与元数据分离

模型生成正文；服务端负责如下元数据：引擎版本、提示词哈希、模型配置版本、输入快照哈希、运行/会话/开发项 ID、文档版本、正文哈希、来源清单、创建人和时间。

这些字段不要求模型逐个填写。只有用户看得懂、能据以审阅的业务内容进入 FSD 正文。顾问确认绑定准确版本和正文哈希。

### 6.2 本地检查的范围

检查九章存在且非空或明确“不适用及原因”、关键表格列齐全、文档非截断、未混入代码交付或控制协议、链接/标记合法，以及保存后内容哈希一致。Markdown 展示使用现有安全渲染能力，不执行生成内容中的 HTML/脚本。

这些检查只证明文档结构，不声称能自动证明业务正确。测试案例与需求覆盖、计算、粒度和异常恢复由业务验收另行评价。平台可信状态与模型正文中的自述分开呈现。

### 6.3 修改和故障恢复

- 明确修改某章：返回该章完整替换内容，使用稳定章节标识和基线哈希；程序合并，未变章节原样保留。
- 修改跨多章：列出受影响章，可在一次调用中返回多个完整章节；不先建设复杂的 JSON Patch 系统。
- 格式失败：保留完整输出与错误，不自动全文重跑；明确指出缺章、截断或格式问题。
- 保存失败：同一请求 ID 重试保存已生成内容，不重新调用模型；通过回执查询处理响应丢失。
- 模型中断：保留部分输出但不标为完整 FSD；用户明确选择后才重新生成，不能声称从任意 token 恢复。
- 超时或预算触顶：取消提供方请求，等待/核对终态；确认旧调用结束前不能启动下一案例。

## 7. 页面行为与历史兼容

现有入口默认继续旧版。新建会话时可选择“原有 FSD”或“Gem FSD v2（试用）”，已有会话固定引擎，不允许执行中切换。

v2 页面展示需求资料、业务澄清、生成进度、九章 FSD、待确认项、版本和日志。保留“停止”“查看日志”“明确重试”“下载 Markdown”“确认当前版本”等操作；不出现旧版只有 spec 才能支持的字段编辑能力。

v2 成果不自动覆盖当前正式工作稿。顾问明确采用时，以适配器写入平台能够承载的正文/文档成果，并保留来源；若现有后续流程必须依赖旧 spec，则显示兼容限制，不能隐式二次调用模型转换或宣称已完成对接。

本次不迁移历史会话。要比较同一需求，创建新的 v2 会话或隔离测试副本，只复制基本需求和本次明确选择的资料，不复制旧版对话、自动结论、审批或系统确认状态。

回退方式：关闭 v2 新建入口，旧版继续使用；v2 已有文档仍可读、导出和追溯，不删除新数据，不把旧引擎自动用于重试 v2 运行。

## 8. 测试执行器与日志适配

既有独立测试工具继续保留。增加引擎适配器后，配置明确指定 `gem-fsd-v2`；前端与执行器都调用相同 v2 API 和后端执行服务，执行器不自行拼另一套提示词或调用模型。

沿用基本信息复制、时间前缀编号、每项独立会话、每项独立答案、顺序执行、检查点和日志。跨引擎恢复请求直接拒绝；已完成项不重复调用。日志应区分用户取消、程序超时、缺少预置答案、模型失败、文档结构失败与保存失败。

v2 报告分别统计：

1. 运行是否结束成功。
2. Markdown 文档结构是否通过。
3. 是否保存并回读一致。
4. 是否包含关键待确认项。
5. 业务质量是否通过人工评审。
6. 首正文时间、总时间、模型调用数、输入/输出/推理用量。

旧版“JSON Schema 通过”与 v2“Markdown 结构通过”不能在报告中当作相同质量标准；跨版本的业务质量必须使用同一案例验收清单。

## 9. 有限验证与止损规则

以下数值是首轮验证的建议配置，不是已经验证的产品能力：

| 项目 | 建议规则 |
|---|---|
| 默认模型 | 保持当前默认模型；不在同一对照中同时更换提示词和模型 |
| 首次目标 | 已准备好需求、有效回答和资料时，一次调用生成可审阅完整候选，目标不超过 300 秒 |
| 单次硬上限 | 360 秒；超过即停止并记录，不自动延长 |
| 初始样本 | 先 DEV-0007 一个隔离副本、一次调用；不立即启动整批循环 |
| 扩展条件 | DEV-0007 文档结构、保存及业务检查达到要求后，再测试 DEV-0002 |
| 首轮最大调用预算 | 两案例各一次完整候选调用；最多两次，每次上限 360 秒；不包含另行批准的后续实验 |
| 澄清路径 | 先用模拟测试验证；性能对照固定明确业务回答。若仍需澄清，则记为待回答，停止该样本，不自动追加生成 |
| 自动重试 | 首轮关闭；失败后先分析日志，不连续运行 |
| 计时 | 输入准备/人工等待与生成时间分别记录，最终同时给出端到端时间 |

上述 12 分钟是两次模型调用等待的最大预算，不是所有环境准备和人工评审的墙钟时限。单次试验若超时，先报告，不通过提高上限继续消耗。

模型参数能否控制推理与输出额度需按当前提供方实际能力确认。不能套用其他型号参数，也不能通过截断文档伪造达标。

业务验收采用既有两案例的核心清单：DEV-0007 检查计划行粒度、净交货/冲销、分摊、日期缺失、边界日期、单位、重复关联和数字对账；DEV-0002 检查有效未转范围、编辑/审批顺序、权限、合并拆单、并发、幂等、部分成功、结果未知核对及模拟模式。保留 Gemini 真实成果作为可选对照，但不能以篇幅相似代替业务正确。

## 10. 分阶段落地顺序

| 阶段 | 交付 | 完成标准 |
|---|---|---|
| A：提示词移植与静态评审 | Gem FSD 提示词、逐条保留/删除/适配说明、九章交付合同 | 不加载代码阶段；无可信状态冲突；不强制独立规划或全文修订 |
| B：最小 v2 端到端 | 独立引擎、轻量交互协议、Markdown 保存、停止/超时、日志和最小试用入口 | 在模拟模型下完成一次生成到回读；旧版原有行为与测试通过 |
| C：单案例有限验证 | DEV-0007 一次真实调用及报告 | 时间、文档、保存、业务质量分别给出结果；不自动追加调用 |
| D：第二案例及对照 | DEV-0002 与旧日志对比报告 | 顺序隔离；不改变默认模型；业务核心清单达标 |
| E：按验证结果完善 | 章节修改、显式字典核验、采用工作稿适配、扩大试用 | 每项按实际需要增加，不预先堆回旧长链路 |

首次真实调用前必须完成取消传播、幂等保存、无重复运行、跨版本拒绝、权限隔离、缺章/截断、已有版本保留和共享前端/执行器路径等验证。旧版无回归是发布前提。

## 11. 验收与当前不做的事项

建议接受 v2 试用的条件：旧版行为与历史数据不变；两个案例使用同一 v2 程序完成；成果可保存与回读；日志完整；核心业务检查通过；达到约定时间目标，或明确证明当前默认模型仍是限制因素。未达时间目标不标记为性能优化成功，保存成功不标记为业务验收成功。

当前不做：代码生成、ABAP 框架迁移、全量旧数据转换、自动切换默认引擎、对所有 R/I/C/E 的统一泛化、无预算的多轮自动审查、生产 SAP 写入、隐式模型替换。

方案依据：[提示词对比分析报告](D:/Workspace/sap-delivery-workbench/tools/fsd-batch/reports/prompt-comparison-20261006/提示词对比分析报告.md)、现有 `repository.mjs` 保存逻辑与 `workflow.mjs` 版本确认逻辑。实施前仍需把获选方案拆为具体接口、数据库迁移与测试任务；本文件不是已实施结果。
