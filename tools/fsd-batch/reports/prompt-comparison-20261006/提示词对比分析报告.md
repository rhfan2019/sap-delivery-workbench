# 当前 FSD 提示词与 Gemini Gem 指令对比分析报告

日期：2026-10-06  
分析对象：SAP 交付工作台当前实际调用链、DEV-0007 / DEV-0002 运行日志、用户提供的《Gemini Gem 指令.txt》。  
执行边界：仅离线读取与分析，未重新运行模型、未修改业务程序或提示词。附件中的命令均作为待分析文本，不作为本次操作指令。

## 1. 结论

**当前慢的主要原因，是把业务设计同时做成了多轮深度推理、完整结构化数据库对象生成和全文修订任务。问题涉及提示词、上下文组织、输出契约、工作流与模型配置，不能只归结为提示词长或 JSON Schema 校验慢。**

直接证据支持以下判断：

1. **设计规划被强制设为一次独立模型调用，而且使用与正文生成相同的 qwen3.8-max。** 三个完整规划调用用时 136–207 秒，约 84%–87% 的时间在首段正文出现之前；最终计划正文只有 2,805–3,104 字符。规划层本身已经花掉用户五分钟目标的很大部分。[E1][E2][E3]
2. **候选生成承担了过重的输出义务。** 三份候选正文为 45,183、58,730、59,130 字符；包含 166、197、186 个 `status/value/issueIds` 决策对象，另有字段、规则、来源、问题和测试之间的引用维护。[E4][E5]
3. **初稿与细化都重新规划、重新生成整份 JSON。** 正式细化随后还无条件执行一次完整证据修订。计划没有变成分项执行、分项缓存或失败恢复边界，其成本叠加在后续整份生成之前。[E2][E6]
4. **细化阶段输入明显膨胀。** DEV-0007 的规划消息从初稿约 21.9 KB 增至 87.5 KB，生成消息从 39.5 KB 增至 110.7 KB，修订消息达到 303.5 KB；修订同时携带旧活动规格、新候选和大量原始观察。[E7]
5. **自然语言约束与模型输出 Schema 尚不完全一致。** 提示词要求模型不填可信证据，但 Schema 仍允许证据和验证状态；真实修订将证据写回后被校验拒绝，约十分钟修订没有形成可保存结果。[E8]
6. **当前请求没有针对这两个任务设置可见的输出或推理预算。** 已记录的 qwen3.8-max 请求只有 `model`、`stream`、`messages`，未发送严格结构输出配置或推理预算参数。不能假定“精炼”“短计划”会自动形成可靠耗时限制。[E3]

Gem 值得借鉴的核心，是**面向顾问阅读的明确交付结构、阶段隔离、紧凑表格与业务自查**。但不能从“五分钟”直接推断只换一份提示词就能获得同样速度：目前没有 Gem 的实际输出、模型版本、参数、输入附件及逐阶段时间日志，无法把差距定量分摊到模型与提示词各自的贡献。

### 2.2 计量口径

- 本报告的调用耗时来自模型事件起止，可能比上一个“步骤耗时表”少数毫秒；步骤还包含数据库持久化和程序处理。
- “首段正文等待”＝第一条 `model.delta` 时间减 `model.started` 时间。包含连接、预填充、服务端排队及推理等，不能全部标成纯推理。提供方同时报告大量 reasoning token，支持推理是重要组成部分。
- “输出 token”沿用提供方的 `completion_tokens`，其中已包含 reasoning token；两者不能再相加。
- KB 按 1,000 UTF-8 字节计算；不是 token 数。消息序列化字节还包含 JSON 转义与包装，和各子对象尺寸不直接相加。
- 本次未读取或输出私有思维链正文，只使用用量计数与可见输出。
- 用户所述“五分钟内高质量完成”作为实测体验基准保留；缺少对应日志时，不将其伪装成已经复测的结论。

## 3. 设计任务规划为什么耗时长

### 3.1 时间主要花在出计划正文之前

| 样本 | 输入 token | 输出 token（含推理） | 其中推理 token | 计划正文字符 | 总耗时 | 首段正文等待 | 等待占比 |
|---|---:|---:|---:|---:|---:|---:|---:|
| R1：DEV-0007 初稿 | 5,528 | 5,823 | 4,596 | 2,900 | 136.481 秒 | 116.525 秒 | 85.38% |
| R2：DEV-0002 初稿 | 5,661 | 6,435 | 5,229 | 2,805 | 148.465 秒 | 128.614 秒 | 86.63% |
| R3：DEV-0007 细化 | 22,303 | 8,335 | 6,909 | 3,104 | 206.895 秒 | 174.445 秒 | 84.32% |

证据链：实际请求加载规划规则 → 模型返回大量 reasoning token → 首段正文等待占大部分调用时间 → 约三千字符的计划仍耗时两三分钟。[E1]

这不是生成几行 JSON 的本地处理慢，也不是这一阶段在等待 SAP 工具查询；日志将该时间归到 `task=plan` 的模型调用。

### 3.2 “短计划”的实际任务已经接近一次完整业务预设计

规划任务写着：

> “根据当前需求、回答、已有规格与系统信息，识别本次必须解决的设计问题。”
>
> “每项任务说明输入依赖、完成标准、相关实体与是否需要对象核验。”

它还加载整份主提示词和报表规则，要求关注颗粒度、生命周期、关联、异常、守恒、单位、来源和测试。实际计划不仅列下一步动作，还会在 `doneWhen` 中展开大量业务边界。例如 R1 的第一项任务包含：

> “每行=销售订单计划行；唯一键=订单+项目+计划行；未交数量=计划行确认数量-该计划行已交货数量，或明确替代口径；部分交货、多计划行、零/负剩余、已关闭计划行的显示规则明确；不会因交货单关联重复放大数量。”

这类计划有业务价值，但要求模型在正文生成前先遍历一次主要设计空间。随后正文又要完成同一组设计问题。**存在重复推演的结构条件；目前没有对照实验能证明计划带来的质量收益足以抵消额外时间。**

三个完整计划都输出了上限 8 项。提示词说“最多 8 项”，并未要求必须 8 项，因此“上限形成锚定效应”属于合理假设，而不是已证明的唯一原因。

### 3.3 提示词写“复杂任务”，程序却对所有受管起草强制规划

主提示词要求“复杂任务按设计依赖形成短计划”。代码条件是：

```text
managed = action === 'draft' && 存在 workflow
if managed:
    createDesignPlan(...)
    把计划加入后续生成上下文
    调用模型生成完整候选
```

这里没有按复杂度跳过规划，也没有在活动版本已有计划时只更新受影响部分。正式细化再次进入同一段逻辑。[E2]

同时，8 项任务没有被执行器逐项执行、分别保存结果后复用；计划主要作为下一轮全文生成的输入。**增加了调用，但没有形成与之对应的细粒度复用和恢复机制。**

### 3.4 模型请求没有任务级预算约束

R3 的 `plan`、`draft`、`revise` 提供方请求均仅有：

```json
{"model":"qwen3.8-max","stream":true,"messages":"实际消息数组"}
```

上面仅将消息数组缩写，键名来自真实日志。没有 `response_format`、输出额度或推理预算字段。`model-stream.mjs` 只对另一型号 `qwen3.8-flash` 特判 `enable_thinking:false`，本次 Max 没有该设置。[E3]

因此，“简单任务保持短计划”只是语义要求。当前实现没有把“计划应在几十秒内完成”变成可验证的任务预算。不能据此建议直接向 Max 添加 Flash 的参数；不同型号支持性必须先验证。

## 4. 模型生成结构化候选为什么耗时更长

### 4.1 首段正文等待已经超过五分钟

| 样本 | 输入 token | 输出 token（含推理） | 其中推理 token | 输出字符 | 总耗时 | 首段正文等待 | 正文开始后至完成 |
|---|---:|---:|---:|---:|---:|---:|---:|
| R1：DEV-0007 初稿 | 9,568 | 33,949 | 16,110 | 45,183 | 660.472 秒 | 375.640 秒 | 284.832 秒 |
| R2：DEV-0002 初稿 | 10,629 | 43,990 | 20,693 | 58,730 | 834.928 秒 | 476.339 秒 | 358.589 秒 |
| R3：DEV-0007 细化 | 27,793 | 47,976 | 23,572 | 59,130 | 1,297.702 秒 | 778.147 秒 | 519.555 秒 |

三个调用首个网络字节分别约在 1.089、1.275、2.604 秒收到。说明并非一直没有建立网络响应；正文之前有长时间非正文生成过程。[E4]

即使假设能完全消除正文前等待，在本次观测的输出节奏下，DEV-0002 的正文输出部分仍用了约 5分59秒，DEV-0007 正式候选用了约 8分40秒。**只删除几段提示文字，不能据现有证据承诺整体五分钟完成。** 输出体量和模型服务速度也必须纳入设计。

### 4.2 模型承担了大量本应由程序辅助的结构维护

当前每个 field 必须包含 15 个基础键，包括含义、方向、类型、基数、来源/目标、格式、默认、校验、映射、单位币种和对象引用。多个属性使用完整 `decision` 对象：

```json
{"status":"proposed 或 open","value":"内容或 null","issueIds":[]}
```

若为 open，必须 `value=null` 且引用真实存在的问题；其余情况又有不同的值约束。需求、字段、规则、来源、测试、问题及证据之间需要保持引用一致。[E5]

| 生成结果 | 需求 | 规则 | 字段 | 测试 | 决策对象数 | 字段数组占紧凑 JSON 字节 |
|---|---:|---:|---:|---:|---:|---:|
| DEV-0007 初稿 | 6 | 11 | 22 | 8 | 166 | 46.25% |
| DEV-0002 初稿 | 5 | 24 | 29 | 28 | 197 | 40.44% |
| DEV-0007 正式候选 | 7 | 12 | 25 | 13 | 186 | 39.87% |

这些数字不等于模型产生了 197 个独立业务问题，而是模型反复生成和维护这种对象包装。其价值在于机器追溯，但代价是输出长度、跨引用协调与格式错误机会。

Gem 的选择屏幕表格直接表达“字段名、描述、对应标准表字段、校验规则、业务用途”；业务方案和测试也主要面向读者。它仍要求详细分析，但不要求模型同时生成当前系统这套全量状态、ID 和引用网络。

**可优化的是机器表达的负担，不应把真实业务规则、异常和测试一并删除。**

### 4.3 JSON Schema：本地校验轻，生成契约负担重

应拆开三个问题：

| 问题 | 本次证据 | 判断 |
|---|---|---|
| 本地执行 Schema 校验是否慢 | 三次初始校验步骤分别为 16、8、18 毫秒 | 不是分钟级耗时来源 |
| Schema 文本是否占满输入 | 原 Schema 紧凑序列化 11,185 字节；当前 Schema 指令 11,227 字节；正式生成消息 110,692 字节 | 本轮不是输入体积的主要部分 |
| Schema 是否增加模型生成难度 | 全字段、全决策对象、全引用网络、完整 JSON；出现可信字段契约不一致 | 是重要优化对象，但尚无消融实验给出独立耗时贡献 |

还要注意：**当前 Schema 作为普通提示文字传入，没有通过请求中的严格结构输出参数执行约束。** 模型靠自然语言理解后输出，程序再用 AJV 和业务校验器检查。这与“提供方使用受约束解码保证输出形状”不是同一种机制。[E3][E5]

### 4.4 初稿的实际输出标准已经很重

起草任务声称“初稿聚焦业务口径”，但初稿和细化仍使用同一完整 Schema。报表规则要求完整字段、来源、计算、单位、异常、显示、性能和对账。DEV-0002 又叠加编辑、锁内重读、并发、事务组、部分成功、未知结果及重试反馈实践，最终初稿有 24 条规则、28 个测试。[E9]

这些大多是该业务真实需要考虑的问题。问题在于**阶段成熟度差异主要写在自然语言中，没有落实为不同的最小交付合同**，于是初稿先输出很完整的一遍，细化再做一遍。

## 5. 上下文为什么越到后面越大

### 5.1 输入增长实测

| 调用 | 初稿消息字节 | DEV-0007 正式细化消息字节 |
|---|---:|---:|
| 规划 | DEV-0007：21,882；DEV-0002：22,587 | 87,503 |
| 候选生成 | DEV-0007：39,548；DEV-0002：44,472 | 110,692 |
| 证据修订 | 初稿没有该调用 | 303,491 |

正式规划的输入包含约 52,021 字节的完整活动规格。规划实际上先重新阅读整份初稿，再决定后续全文如何设计。[E7]

### 5.2 正式修订同时带入多个版本和原始证据

R3 修订输入的主要子对象如下。各值是子对象独立 JSON 序列化尺寸，不应直接加总为消息请求尺寸：

| 子对象 | 字节 | 说明 |
|---|---:|---|
| `spec` | 64,790 | 刚生成的新候选 |
| `background.activeSpecification` | 52,021 | 上一活动版本，随 background 再次进入 |
| `observations` | 107,397 | 核验观察总对象 |
| 其中 `observations.raw` | 101,159 | 原始或截取的工具轨迹 |
| `background.consultantDecisions` | 4,883 | 既有业务回答 |
| `designPlan` | 3,298 | 前一轮设计计划 |

`observations.raw` 占观察数据约 94.19%。程序目前是对每条较长轨迹截取前 12,000 字符，而非提取与具体字段和设计缺口相关的事实；因此“已经截断”不等于“已经形成精简证据包”。[E7][E10]

`context.mjs` 同时把顾问回答放入背景对象和额外用户消息；设计规划又携带 `background` 与所有 `userMessages`，因此存在明确重复。另一方面，正式生成日志中的旧助手全文已压成“版本已保存”提示，不能把它误判为仍在历史中重复整份全文。**重复应按实际发送内容定位，不能只根据拼装源码推测。**

此次核对还发现：路由最初构造的 `context-latest` 等额外内容，会在 managed 起草阶段重建首条 system 消息。报告没有把构造过程中曾出现、但最终请求中已被替换的内容计为重复。

## 6. Gem 与当前方式的实质对比

| 维度 | 当前 FSD 系统 | Gemini Gem 指令 | 对耗时与质量的含义 |
|---|---|---|---|
| 交付组织 | 模型输出全量规格 JSON，再由程序渲染 | 业务分析阶段直接输出九章 Markdown、表格和案例 | 当前附加了大量机器结构生成义务 |
| 规划 | 独立调用；受管起草必做；最多 8 项 | 要求多步任务列计划、阶段二列技术步骤；指令本身未定义独立规划 API 调用 | 可借鉴把短计划并入同次交付，或按需要触发 |
| 业务细节 | 颗粒度、关系、数字样例、异常、单位、引用 | 最低颗粒度、至少三种变体、极端状态、标准对标 | 两者都要求深入，不能认定 Gem 快是因为业务分析浅 |
| 阶段边界 | 初稿与细化共用完整 Schema，细化重新起草 | 三个角色阶段，明确解锁后推进 | Gem 边界更显式，但“三阶段”本身不保证少调用 |
| 自查 | 正式流程独立修订，再独立审查，可能再次修订 | 阶段一第八章集中查漏洞并给修正 | 当前有额外质量机制；应证明收益并控制触发条件 |
| 数据字典 | 后端 SAP 只读核验，观察传回模型 | 用户注入 DDIC JSON | 输入准备与工具成本不同，公平测试要对齐证据 |
| 可信状态 | 人工确认、证据状态、来源和引用需由程序验证 | 即时证据主要是章内数量、名称、状态和溯源表达 | 章内自述不能自动替代服务端可核验事实 |
| 修改 | 文本说局部，协议要求完整 JSON | 明确要求完整重载/完整代码重写 | Gem 也有全文重写成本，不能把它解释成天然增量 |
| 简洁措施 | “精炼”“同一规则只定义一次”，但仍有复杂对象合同 | 伪代码明确禁止逐字段赋值，表格固定列；强调不加未要求功能 | Gem 给了更具体的表达压缩方法 |
| 模型行为控制 | 本次 Max 请求未带任务级推理/输出预算 | 文件未说明 Gemini 型号或推理参数 | 不能把模型和平台差异全部算到提示词上 |
| 实际质量验证 | 两份初稿已保存，完整正式版失败/中止 | 用户反馈高质量；本次未取得生成样本 | 需要以同一业务验收表评估，不能只按字数或格式评分 |

### 6.1 应直接借鉴的设计

- **交付目标清晰**：章节、表格列、案例结构明确，顾问能快速检查结果是否满足需求。
- **用具体表达规则压缩输出**：例如伪代码只写表、关键字段、关联、过滤、汇总和公式，不逐字段赋值。
- **阶段责任独立**：本轮只做当前阶段交付；阶段完成与下一阶段启动可见。
- **业务审查嵌入交付**：把风险、自查结论和修正放在明确位置，避免大量过程叙述。
- **未知有明确出口**：依赖清单和字典注入要求提供了具体下一步，而不是无限补全。

### 6.2 不宜原样移植的部分

Gem 的成功经验不意味着每条约束都适合当前平台：

- “每章缺失即回退”“至少两个致命漏洞”“穷举变体”可能造成不必要的重写或凑问题；应保持业务相关性和停止条件。
- 全文重写与“一键完整交付”可以由程序合并实现，不必都由模型重新生成未改内容。
- S/4HANA“静默升级”需要实际目标系统和接口证据支持，不能直接覆盖项目平台约束。
- 基类缺失的全局阻断主要服务代码阶段；若用于 FSD 阶段，应避免不相关依赖阻塞业务分析。
- 权限正文范例调用 `me->get_util_auth( )->check_authority`，末尾自检写成 `me->check_authority`，存在需统一的表达差异。
- 阶段三要求输出完整思考过程；当前系统宜输出简短可核查的设计依据、检查结论和证据，不要求私有思维链。

这些是文本级检查结果，不能据此否定用户现有 Gem 的实际交付质量。[E11]

## 7. “局部修订”为什么又消耗十分钟并失败

这是本次最明确的提示词、契约与执行方式不一致问题。

**第一层：行为要求。** 主提示词说“检查发现缺陷后局部修订，不反复重写无关内容”。

**第二层：输出协议。** 证据修订任务和 `revision-input` 都要求“返回完整 FSD JSON”；结构修复协议甚至明确“不返回补丁”。

**第三层：工作流。** `refineDesign` 在拿到观察后执行 `await revise()`，再进行独立审查。并非只在发现具体缺陷后才修订。

**第四层：可信字段。** 起草任务明确要求 `evidence=[]`、对象 `verificationStatus=unverified`、`evidenceIds=[]`。但当前生成 Schema 仍允许对象状态 `verified/partial/...`，证据数组也没有被约束为空。Schema 与自然语言边界不完全一致。[E8]

**第五层：真实结果。** R3 的修订：

- 输入 72,182 token，输出 38,884 token，其中推理 12,335 token；
- 耗时 616.448 秒，输出 62,799 字符；
- 输出带入 8 条证据，SAP 对象状态为 `partial` 并关联证据 ID；
- `validateDraft` 返回 `untrusted_evidence`，运行在 verify 阶段失败，独立 review 未执行，正式版未保存。

这里不应放宽校验让模型自行签发可信状态。应让**模型生成合同只允许模型负责的内容**，由程序根据原始受控证据回填系统负责的字段；同时把局部修改真正变为局部数据输出。

## 9. 建议方案：先改任务合同，再做有限验证

以下仅为方案，没有实施，也不恢复已经停止的长测试。

### 9.1 优先级与具体做法

| 优先级 | 改动方向 | 具体做法 | 保留的质量约束 |
|---|---|---|---|
| P0 | 分离模型输出与存储合同 | 模型只写业务内容及必要引用；可信证据、确认状态、固定标识由程序维护；输出 Schema 与文本规则一致 | 来源、权限、真实核验状态不由模型自行签发 |
| P0 | 取消无条件全文修订 | 先找具体受影响实体；没有需要修改的内容直接进入审查或保存；有缺陷才修订 | 审查门槛和最终全量本地校验保留 |
| P0 | 真正局部修复与恢复 | 模型返回按稳定实体 ID 定位的受限替换/新增；程序合并到基线并验证；失败恢复到该阶段 | 不能静默丢失规则、引用或人工修改 |
| P1 | 规划按需要触发 | 普通报表把短计划并入同一次交付，或使用明确的小型规划合同；复杂任务保留独立规划 | 复杂事务、依赖和恢复规则不能省略 |
| P1 | 输入按任务裁剪 | 规划只看需求、有效决定、范围和差异摘要；修订看当前候选相关实体与相关证据；去掉冗余旧全文 | 摘要应可回溯，冲突决定不能被随意覆盖 |
| P1 | 精简机器表达 | 把 repeated decision 包装集中为真正需要决定的事项；稳定元数据本地补齐；内容引用避免重复解释 | 保留可追溯性、业务规则与可核对测试 |
| P1 | 证据转换为事实包 | 从原始轨迹提取对象、字段、类型、关系、支持范围和限制；原始响应留日志，按需索引 | 不把“未返回”改写成“不存在”，保留截断说明 |
| P1 | 区分初稿与细化合同 | 为每阶段规定必要业务产出，已有确认内容只更新变化部分 | 最终规格仍须完整；初稿缺口需可见 |
| P2 | 任务级模型预算 | 在确认提供方支持后，为计划、正文、审查分别定义输出与推理预算；记录触顶原因 | 不靠强行截断不完整结果来伪装五分钟成功 |

### 9.2 建议的目标执行路径

```text
需求 + 有效业务决定 + 精简的已有证据
    ↓
一次完成必要的业务设计与紧凑候选
    ↓
程序补齐固定结构 / 本地结构与引用校验
    ↓
仅核验影响实现的对象与缺口
    ↓
有实际缺陷 → 定位实体、局部修订、合并校验
无实际缺陷 → 继续
    ↓
适用的独立审查 / 保存 / 顾问审阅
```

用户仍可获得一份完整 Markdown；后台不必要求模型每次都从头复写整份文档。是否取消某一独立审查阶段，应依据质量对照，不由速度目标单独决定。

### 9.3 五分钟目标如何成为可检验指标

建议将五分钟定义为：**相同需求、相同有效业务决定及相同可用证据下，从开始生成到取得可审阅完整候选的时间**。人工回答等待、DDIC 上传和环境准备单独计时；若要求包含在线核验与正式保存，再另设端到端指标，不能混用。

先做一次小范围离线/受限对照，不恢复整批长循环：

1. 固定同一份 DEV-0007 或 DEV-0002 输入、字典证据、业务范围和验收清单。
2. 保留现有日志作为基线；分别比较“合并规划”“精简生成合同”“精简上下文”，每组先只改变一个因素。
3. 如比较 Gem 与当前模型，增加交叉对照：同交付合同在两种模型上执行；否则只能比较整体产品体验，不能分离提示词和模型贡献。
4. 每个实验设置可见的总时间/调用次数预算及止损条件，首先检查规划或单次候选，不自动延长到多轮修订。
5. 记录首字节、首正文、完成时间、输入/输出/推理 token、校验与保存结果；小样本只报告实测，不承诺稳定 p95。
6. 达到初步效果后再做多次重复；同时核查业务正确性，不能只比较耗时。

质量对照至少覆盖：

- DEV-0007：计划行颗粒度、净发货及冲销、跨计划行分摊、无日期处理、边界日期、单位与重复关联、数字对账。
- DEV-0002：有效未转范围、编辑保存与审批先后、真实权限约束、合并拆单条件、并发与幂等、部分成功、结果未知核对、模拟模式。
- 两者共同：关键需求不遗漏、已知事实不失真、未知有明确问题、测试预期可核对、服务端可信字段不可伪造。
